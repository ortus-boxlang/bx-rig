    BxRig command contract

    Target (2026-11-09): Hyprland + Noctalia on CachyOS, KDE kept side by side; see plan.md section 19. setup is the headline command.

    Status (2026-11-15): built. This file started as the proposal and became the design record; sections 1 to 12 are the rules and the first build, section 13 onward holds one decision section per feature, 14 the installer and the wizard. Where a sentence here and the code disagree, the code wins: docs/reference/cli.json is the command registry (96 commands and their flags, usage and examples), docs/reference/commands.md is generated from it, and bxrig help NAME prints the same text. The legacy tree in artifacts/legacy/original/ is the v0.10.0 source, kept as a feature reference and never modified.

    1. Grammar

    bxrig <command> [subcommand] [args...] [--yes] [--dry-run] [--json] [--quiet] [--force]
    • A command is one word from docs/reference/cli.json (setup, keys, menu, record, browser, ...); its subcommands and positional arguments are in its usage lines. Groups in the reference (Start here, Install, Desktop, Look, System, Develop, Tools) only organise the page.
    • Mutating verbs (install, apply, remove, restore, enable, disable, set, ...) need --yes; read-only ones (list, show, status, plan, doctor) never do.
    • Flags are checked against the registry before anything runs: a flag the command does not list is a usage error (exit 2, the usage line is printed); secrets run passes everything after its own flags through. An unknown command is exit 2 too.
    • CLIGetArgs() puts flags in args.options and the words in args.positionals; a flag with a value is written --name=value (the form --name value is a flag plus a positional on MatchBox).

    2. Mutation rules (apply to every mutating verb)

    1. No --yes: print the exact plan, change nothing, exit 2.
    2. --dry-run with --yes: print the exact plan, change nothing, exit 0.
    3. Preflight everything before the first mutation. A preflight failure means zero changes.
    4. Never escalate privilege silently. sudo is only called for pacman steps shown in the plan.
    5. Never run AUR builds as root (exit 4).
    6. Every config file touched goes through the config service (backup, atomic replace, journal). No direct writes.
    7. Output lists succeeded and failed items separately. No rollback is promised across pacman and yay.
    8. External installer scripts (bvm, mvm, toolchain node's nvm, catalog source: script) are downloaded to a temp file, their url and sha256 are printed, and they run as the normal user (never root) with no confirmation gate and no flag: the typed EXECUTE and --allow-external-scripts were removed on 2026-11-10 (owner: running them is the point of the command). Decision 2026-11-09: no checksum pinning for these scripts.
    9. Subprocesses are launched with argument arrays, never through a shell string. The one place that starts a process is util/Proc; the few sh -c wrappers pass every value as a positional argument (detach, recording, the pull-down shells).
    10. The plan, dry-run and run protocol is one class, util/Mutation, reached through Out.plan( ... ): no --yes prints "Plan: TITLE", the extra lines and "Nothing was changed. Add --yes to apply." (exit 2); --dry-run prints "Dry run: TITLE" and the same lines (exit 0); the first failing step ends the run (exit 6). A ratchet in tests/dry-test.sh forbids hand-written plan footers.
    11. Documented exceptions to --yes: a command that changes only your own settings or starts or stops a program acts at once and takes --dry-run (themes, appearance, time format, display, notify, tiling, runner set, layout, record, webcam, window, browser private, files here, dictation toggle). Anything that installs packages, writes system files or changes login behaviour always needs --yes.

    3. Exit codes

    CodeMeaningExample
    0Success or no-opalready installed, or --dry-run
    1Check negativepackage-status says missing
    2Usage error or missing confirmationno --yes, unknown flag
    3Timeout, or item unavailablepacman lookup timed out, package not in any repo
    4Precondition failedroot with AUR, not Arch, Java missing, not KDE where required
    5Official (pacman) phase failed
    6AUR (yay) phase failed
    7Partial successsome items done, some failed; --json lists both
    8Config conflictdrift detected, symlink or special file at target, concurrent run lock
    9Internal errorbug, unexpected exception (Application.bx onError prints it and exits 9)
    10An update is availableupdate check only

    The codes are frozen. tests/cli-contract-test.sh and the per-command tests check them; a bad name is exit 2 everywhere (it was 4 in some commands before the Names helper); an unknown command or flag is exit 2.

    Names in code. src/bxrig/util/Exit.bx names every code: ok 0, negative 1, usage and plan 2, timeout 3, precondition 4, official 5, failed 6, partial 7, conflict 8, internal 9, update 10. Cli.say, Cli.fail, Out.say and Out.fail take a name or a number; an unknown name throws. Command classes write the name (variables.out.say( "precondition", ... ), CLIExit( xit.usage() ), return new bxrig.Exit().ok();), so a typo cannot turn into a wrong exit code. The numbers on the wire are the table above. tests/dry-test.sh fails on a bare number as the code argument of say/fail and on CLIExit( N ) in Main.bx (130, Ctrl+C, is the exception).

    4. --json

    With --json a command prints one JSON object on stdout and no human text (Cli.envelope):

    {
  "schema": 1,
  "command": "profile install",
  "version": "0.11.0-dev",
  "ok": false,
  "exit": 7,
  "dry_run": false,
  "data": { "done": [], "failed": [], "skipped": [] },
  "warnings": []
}

    data is different for every command (the package commands put would_install, done, failed and skipped there, section 11); ok is true when exit is 0. A plan is exit 2 with the plan in data; a dry run is exit 0 with dry_run true.

    5. Catalog (single source of truth)

    The catalog is catalog/apps.json (schema 4, 349 apps today, version in catalog_version: what each app is) plus one install file per distribution, catalog/install/{arch,suse,debian,ubuntu}.json (how to install it there; see "Distributions"), packed into the binary as a resource (src/resources/catalog). It started as the legacy apps.json (482 entries) and replaced the hardcoded lists. The findings below are the 2026-11-09 audit of that legacy data and are kept as the record of why the catalog looks as it does.

    Entry schema (legacy fields kept, new fields marked):

    FieldNotes
    id, name, kind (desktop tui web), category, descriptionas legacy
    source (pacman aur pkgbuild script manual web), targetpackage name, or URL for web and script
    pkgbuild source: repo, path, refBuild with makepkg as the normal user from a PKGBUILD in a public git repo, pinned to a full 40-character commit (catalog check rejects anything else), then install the result with pacman. Used for desktop apps packaged in omacom/omarchy-pkgs. The PKGBUILD is shown before it is built.
    check (for script)argv array that exits 0 when installed, for example ["command","-v","pi"]
    defaultbase tier flag
    source_status, source_confirmedlegacy provenance flags, kept
    profiles (new)list of profile ids
    deps (new)other catalog ids
    check (new)optional post-install check, argv array
    verified_on (new)date the target was confirmed against real repos

    Findings from the legacy data (historical, decisions recorded 2026-11-09):

    • Unverified sources. 176 entries are source: manual (95 tui, 81 desktop). Their package names are unverified. Proposal: a CI job that checks every pacman/aur target against real repos (Arch container, AUR RPC) and fails on unknown names. manual entries stay installable only by explicit user action.
    • Default list mismatch. 61 flagged default (29 pacman, 18 aur, 14 web). app-profile.json base lists 46. 20 defaults are not in that base list (for example ark dolphin dolphin-plugins kio-extras rclone fuse3 sshfs nfs-utils cifs-utils podman-desktop tabby beekeeper-studio google-docs google-sheets google-slides kompare filelight ffmpegthumbs kdegraphics-thumbnailers kimageformats). 5 base entries are not flagged default (dbeaver filezilla krdc podman-tui rustdesk). The 61 flags win. The 5 dropped base entries are dbeaver (pacman), filezilla (pacman), krdc (pacman), rustdesk (aur) and podman-tui (manual). Pending: keep them as curated (not default), or re-flag any as default.
    • Browsers. brave is aur (brave-bin) and default. A fresh default install therefore needs yay on day one. Decision: bootstrap installs yay only if it is not already present.
    • Preserve list. Legacy preserve (CachyOS, KDE Plasma, Hyprland, Noctalia, existing user configs) becomes enforced rules, not just text.

    Named profiles keep the existing four (core jvm containers terminal) and are expressed as catalog profiles tags. Later profiles (web backend ai ops desktop full) are added only after package names are verified.

    Ship vs embed (pending confirmation): the default catalog is embedded in the binary at build time, so there is one file to ship and it always matches the code. An optional ~/.config/bxrig/catalog.json adds entries or sets default/profiles on existing ids. It is validated against the same schema and can never delete or replace an embedded entry's target, so a bad override cannot redirect an install.

    6. State and config layout

    ~/.config/bxrig/            same root as legacy
  bxrig.json                global settings
  catalog.json                optional user additions (merge-only)
  ai.json menu.json shortcuts.json ...   one file per feature, as legacy
~/.local/state/bxrig/
  journal/                    one record per apply: files, hashes, backup paths
  backups/                    backups, indexed by the journal
  lock                        single-writer lock

    config list|diff|apply|restore work from the journal, so restore needs only an id. Retention default: keep the last 20 per file. Open: this applies to the user's config files that BxRig writes, not to the legacy source tree.

    7. Test contract

    • A snapshot test freezes bxrig help, the exit-code table and the --json schema.
    • Every mutating verb needs these cases: success, no-op, invalid input, dependency failure, privilege rejection, partial failure, recovery.
    • Real-system cases run in tests/arch/ (non-root, real pacman). Cases needing KDE, Wayland or hardware are marked manual and tracked in the acceptance log.

    8. Catalog check, validation and reporting

    bxrig catalog check [--json] [--online] plus a CI job that runs it in the Arch container.

    Offline validation (always, no network): schema version; unique ids; enums for kind/source; web targets are https with no credentials or control characters; package targets match ^[a-zA-Z0-9@._+-]+$; default entries have a non-manual source; profiles and deps reference existing ids; no dependency cycles.

    Online verification (--online, CI): every pacman target must resolve with pacman -Si (or -Sg for groups); every aur target must resolve through the AUR RPC (/rpc/v5/info); manual targets are probed against both and reported as promotable. Results are stored per entry as verified_on and a status: ok, moved (listed source is wrong but another source has it), missing, unverified.

    Reporting: a table by status and source for the console, --json for tools, and a markdown report in the CI step summary and artifact. Policy: missing entries with default: true fail CI; missing non-default entries are warnings listed in the report; moved entries are warnings with the suggested fix.

    First measurement (2026-11-09, stock Arch core/extra only, so CachyOS repos and multilib are not covered):

    CheckResult
    pacman targets (118)111 resolve, 7 do not: 5 exist in AUR (git-cola insomnia localsend ulauncher wlogout), 2 found nowhere (intellij-idea-community-edition, swww)
    aur targets (64)40 resolve in AUR, 11 are now official (doggo impala nwg-dock-hyprland opencode podman-desktop rio spotify-launcher superfile television warehouse zenmap), 13 found nowhere (beeper ctop dbgate espanso grokbot herder inshellisense notion-desktop pi-agent tmog todoist upnote zap-whatsapp)
    manual targets (176)93 are official packages today (promotable, for example jq ripgrep-all tmux kitty starship terraform kubectl), 83 are not

    The check must also run against the CachyOS repos on a real CachyOS machine before any missing entry is removed.

    10. Implemented so far (2026-11-09)

    • config list|diff|apply|restore|history (section 6 design; lock is a file created with fileWriteExclusive, temp files and journal records are created exclusive with their mode).
    • Global flag check and the --json envelope (sections 1 and 4) for the read-only commands.
    • catalog list|show|groups|check|version: the catalog is schema 4 plus the install files (catalog/README.md) and is packed into the binary as a resource (src/resources/catalog, read by src/bxrig/CatalogData.bx). Filters use the --name=value form (--tier=default --group=infra), because MatchBox CLIGetArgs takes --name value as a flag plus a positional. catalog check is offline: errors exit 1, warnings (unpinned pkgbuild refs, default entries without a package) do not. The user override file is deliberately last (extensibility phase).

    11. Package commands on the catalog (B2, decided 2026-11-09)

    Applies to plan, install-plan, install, optional-*, profile-*, package-status, package-source. All read the embedded catalog (schema 3). Hardcoded lists in Main.bx go away.

    Selection

    bxrig install                       # tier default
bxrig install ID [ID...]            # exactly these apps
bxrig install --profile=NAME        # a profile
bxrig install --optional            # default tier plus optional tier
    • Naming an app is enough. There is no --aur flag: anything in the catalog installs from its source (pacman, aur, pkgbuild, web).
    • Unknown id: usage error (exit 2), nothing runs.
    • Skip reasons: optional (not selected), wrong_shell and unresolved (catalog has no installable source yet; a named unresolved app is reported failed, exit 3).
    • Already installed apps are skipped with reason installed.
    • Section 2 still applies: no --yes prints the plan and exits 2; --dry-run --yes prints it and exits 0. AUR and pkgbuild builds never run as root (exit 4).
    • Profiles live in the catalog (0.3.0): a top-level profiles list and, per app, a map profile id to default/optional. --profile=NAME installs the profile's default members; --optional adds its optional ones. See catalog/README.md.
    • Shells: an app may carry shells (hyprland, plasma). The running shell comes from XDG_CURRENT_DESKTOP, overridable with --shell=hyprland|plasma|all. Non-matching apps are skipped: wrong_shell; a named app still installs.

    Per-source steps

    sourcestep
    pacmanone pacman -S --needed call for all pacman apps (sudo shown in the plan)
    aurAUR helper (yay) as the normal user, apps one at a time
    pkgbuildPKGBUILD shown, makepkg as the normal user, result installed with pacman
    weba .desktop launcher in ~/.local/share/applications/bxrig-<id>.desktop running brave --app=URL (written atomically, no package). The resolver adds brave to the plan when a web app is selected and brave is not installed.

    Result shape (--json, inside the section 4 envelope)

    data for plan, install-plan and install:

    {
  "selection": { "mode": "default|ids|profile|optional", "ids": [], "profile": null },
  "would_install": [ { "id": "git", "source": "pacman", "targets": ["git"] } ],
  "done":    [ { "id": "git", "source": "pacman" } ],
  "failed":  [ { "id": "docker", "source": "pacman", "error": "target not found" } ],
  "skipped": [ { "id": "jq", "reason": "optional" } ]
}
    • plan and --dry-run fill would_install and leave done/failed empty. A real run fills done/failed and leaves would_install empty.
    • Exit: 0 all done or nothing to do; 5 pacman phase failed, 6 AUR/pkgbuild phase failed (only when nothing succeeded); 7 some done and some failed.
    • package-status ID exits 0 when installed, 1 when missing; data is { "id", "source", "installed": true|false }.
    • package-source ID prints { "id", "source", "targets", "tier", "group" }.

    Human output is the same lists, one app per line with its source.

    12. Implemented so far, B2 (2026-11-09)

    • Catalog 0.3.0: profiles, per-profile tier, shells (section 11, catalog/README.md).
    • Resolver class (selection) and Packages class (read-only commands). plan, install-plan, optional-plan, profile-plan, profile-install-plan, package-status, package-source, profile-list, desktop-list, tui-list, web-list, optional-list run on the catalog. Installed state comes from one pacman -Qq call (web apps: launcher file).

    13. Desktop setup (decided with the owner 2026-11-09 and 2026-11-10; all built)

    • Exception to --yes: tiling on|off acts at once (a reversible user setting meant to sit behind a shortcut). status exits 0 on, 1 off, 4 not installed.

Choosing the password: by default one is generated. --password-file FILE uses the first line of a file you made; --ask-password asks twice at the terminal without echo (/dev/tty, so it needs a terminal; the plan never prompts). A password is never a command-line value, so it cannot land in shell history or the process list. It must be 8 to 128 characters with no whitespace (OpenSearch also needs upper and lower case, a digit and a special character). It applies only when the container is created (the image sets it on first start of the data volume): a second start never changes it, an existing container refuses one, and a kept data volume (from remove --keep-data) keeps the password it was made with (a different choice is refused). Engines without a password (Redis, Chroma, Qdrant, Weaviate) and Couchbase (set in its web console) refuse the options. The user name is fixed per engine (postgres, root, admin, elastic).     • Values are passed to secret-tool and to programs through standard input and the process environment, never through a command line, a temp file, a log, or answers.json.
    • set is interactive on purpose and needs no --yes.
    • Exit codes: 0 done, 2 usage or plan without --yes, 4 precondition (bad name, secret not set, no value), 6 the store failed. Loading into shells (default is per command, global is opt-in per key):
    • secrets apply [--yes] writes ~/.config/bxrig/secrets.sh (bash, zsh) and secrets.fish. They hold no values: one wrapper per agent command whose key is stored (claude() { bxrig secrets run ANTHROPIC_API_KEY -- command claude "$@"; }). secrets set runs it automatically. The shell init templates source these files.
    • secrets global on NAME --yes | off NAME | show: exports a key to every new shell. on prints a warning first (every program, including AI agents and what they run, can read it). The values go to a session cache, $XDG_RUNTIME_DIR/bxrig-secrets.env and .fish (mode 600, tmpfs, wiped at logout), never to a config file. The loader files call secrets unlock once per login when the cache is missing (the keyring's single unlock prompt); secrets lock removes the cache. A globally exported key gets no wrapper. Moving machines and the keyring:
    • secrets export FILE [--plain] [--force] --yes: all stored secrets as export NAME='value' lines, encrypted with a passphrase by age -p (age asks on the terminal; the file is mode 600). --plain writes a readable .env instead (mode 600; the plan says so). An existing file is kept unless --force.
    • secrets import FILE [--overwrite] --yes: reads an age file or a .env file; the plan lists each name as new, same or differs. A name that already has a different value is kept unless --overwrite. New machine: install.sh, init --answers answers.json, secrets import, dotfiles apply.
    • secrets setup [--keyring=kwallet|gnome-keyring|none] [--yes] [--dry-run]: checks for a Secret Service on the user D-Bus (running or activatable). Installs libsecret (secret-tool, repo core) and age (repo extra) when missing; when no keyring exists, also kwallet on Plasma or gnome-keyring elsewhere, or the one named. --keyring=none installs no keyring and saves the file backend.     13.30 One-line installer, update channels, updates and notifications (decided with the owner 2026-11-13)

Limit: the very first curl | bash still trusts the script it downloads (TLS and the bucket), so the signature protects the files the script fetches and every later update; verify install.sh.sig by hand with keys/release.pub for a stricter first install.

Restart rule: reboot_pending when a waiting update replaces a kernel (linux and its lts, zen, hardened, rt, cachyos flavours, not headers, docs or driver modules), systemd, glibc, linux-firmware, a microcode package or the NVIDIA driver; reboot_stale when /usr/lib/modules/$(uname -r) is gone; needs_reboot is either.     13.37 Power (decided with the owner 2026-11-13)

    • bxrig power status|profile|lid|hibernate|charge-limit|setup|doctor. profile [performance|balanced|saver] uses powerprofilesctl get|set (saver is power-saver).
    • status --json (2026-11-17, the Power panel reads it): data.battery[] has one entry per BAT* with name, percent, status, state (charging|discharging|full|not_charging|unknown), watts (power draw), time_remaining_minutes (to empty when discharging, to full when charging), health_percent (full over design capacity), cycles, charge_limit and charge_limit_supported. Values come from sysfs (energy_now/power_now or charge_now/current_now, *_full, *_full_design, cycle_count).

Without battery or ac both get the action. Ready: a plan (exit 2) until --yes, then systemctl hibernate --no-block (without --no-block the call would wait until the machine wakes up). The initramfs resume hook cannot be read reliably and is not checked. doctor shows the same checks as hibernation (swap), resume and hibernate-kernel.
    • charge-limit [PERCENT|off|status] [--yes] uses the kernel attribute charge_control_end_threshold of each BAT* (Linux ABI sysfs-class-power: "a battery percentage level, above which charging will stop"; 0 to 100, drivers round to what the hardware supports). PERCENT is 40 to 100. It writes /etc/systemd/system/bxrig-charge-limit.service (a oneshot that writes the value at boot and after suspend, hibernate and hybrid sleep, because some firmware resets it) with sudo install, then daemon-reload, enable --now and restart. off (or 100) disables and removes the unit and writes 100 to the attribute. status is information (exit 0, supported, limit, persisted). On a laptop whose battery has no such attribute PERCENT and off exit 4. A plan (exit 2) without --yes. Not verified on real hardware (the fake sysfs of power-test.sh only).

On a machine without a battery it does nothing (exit 0, skipped: "no battery") unless --force. The init plan has an optional power-setup step behind the answer power_setup; no wizard question exists yet.
    • doctor checks battery, the two daemons, the lid action, zram, and (laptops only) the hibernation checks and whether the battery has a charge limit. Problems are reported, never fixed silently.
    • Not built: configuring hibernation (resume offset, initramfs hook) and TLP; battery display and brightness stay with Noctalia and powerdevil. CachyOS ships no laptop power tooling (cachyos-settings pulls zram, ananicy, inxi, iw, wireless-regdb), so this is ours.

    • Detection needs no root and no external tool.     13.41 NAS as a first-class namespace (decided with the owner 2026-11-13)

    • bxrig nas keeps every NAS you use in ~/.config/bxrig/nas.json (name, host, protocol smb or nfs, user, optional SMB version, and the shares you mounted). discover browses the network with avahi-browse -rtp _smb._tcp and _nfs._tcp (IPv4 only). setup installs cifs-utils nfs-utils smbclient avahi nss-mdns rsync and enables avahi-daemon (a plan without --yes; every tool was checked in the Arch repos and its binary exists after install).
    • add NAME --host=H needs --user and a password for SMB (--ask-password, typed hidden, or --password-file=F); the password goes to the keyring as BXRIG_NAS_<NAME>_PASSWORD and never into nas.json. NFS needs neither. Names are ^[a-z][a-z0-9-]{0,30}$.
    • shares NAME lists SMB shares with smbclient -g -L HOST -A AUTHFILE (the auth file is a private temp file, deleted after; no password on a command line; IPC$ and other hidden shares are dropped) or NFS exports with showmount -e --no-headers.
    • mount|unmount NAME SHARE mounts at ~/NAS/NAME/LEAF (BXRIG_NAS_HOME overrides) with sudo mount -t cifs|nfs; the SMB options are credentials=/etc/bxrig/nas/NAME.cred,uid,gid,iocharset=utf8,file_mode=0600,dir_mode=0700 plus vers= only when you set one (otherwise the kernel negotiates the highest version both sides support). The credentials file is root-only (mode 600) because mount.cifs reads it as root; the plan says so.
    • auto on|off NAME SHARE writes <escaped-path>.mount and .automount units to /etc/systemd/system (Options=...,nofail, TimeoutSec=20, TimeoutIdleSec=600, wanted by multi-user.target), runs daemon-reload and enable --now, so a sleeping NAS never blocks login. off disables and removes them; a NAS with automatic mounts is not removed (exit 4) until they are off.
    • test NAME [SHARE] checks: reachable (TCP 445 or 2049), signed in or exports readable, mounted (findmnt), writable (a probe file), free space. Exit 4 when a check fails.
    • sync NAME SRC --to=SHARE[/PATH] is a plain rsync -a mirror to a mounted share. Nothing is deleted from the NAS unless you add --delete, and the plan says so in capitals.
    • use NAME SHARE [--path=bxrig-backup] records targets.nas-NAME in ~/.config/bxrig/backup.json ({type: nas, nas, share, path}); backup data setup reads it.
    • Verified: tests/nas-test.sh with fake avahi-browse, smbclient, showmount, findmnt, rsync, sudo and a fake /etc. Not verified on a real Synology: DSM share permissions, SMB signing, NFS export options, nss-mdns name resolution.

    13.43 Backups: the config layer (decided with the owner 2026-11-13)

    • Three layers, one command. bxrig backup config (your BxRig setup), backup snapshots (the system, Btrfs with snapper) and backup data (your files, restic) are built in that order; backup send and backup export move any of them, and timemachine shows them all. This section is the config layer; the others are added below as they land.

    • A snapshot is ~/.local/share/bxrig/backups/config/ID.tar.gz (mode 600) plus ID.json. ID is yyyyMMddTHHmmss (with -xxxx when two land in the same second). Inside: files/ (paths under your home), packages.txt (pacman -Qqe), foreign.txt (pacman -Qqm), meta.json, and secrets.bxs only with --with-secrets (the output of bxrig secrets export, encrypted with a passphrase you type).

    • What is tracked (under your home): .config/bxrig, hypr, noctalia, ghostty, kitty, foot, alacritty, starship.toml, nvim, btop, fish, git, mimeapps.list, xdg-terminals.list, .zshrc, .bashrc, .gitconfig, .ssh/config. backup config add|remove PATH changes the list (stored in backup.json); SSH keys, gnupg, .. and absolute paths are refused. .git, node_modules and *.log are skipped.

    • Restore shows a plan (which files are created or replaced; exit 2 without --yes), takes a safety snapshot of the present first, then copies the files back (--only=PATH limits it). --packages installs the explicit packages that are missing and exist in the repositories with sudo pacman -S --needed --noconfirm; AUR and local ones are listed for yay, never installed from here. diff ID compares a snapshot with now (files same, changed, missing, and missing packages).

    • Automatic: auto is on by default. Before update apply, system update, init, reinstall and refresh (with --yes, never --dry-run) a snapshot is taken quietly, with the reason before <command>; it never stops the command. The newest 30 are kept (prune --keep=N).

    • Verified: tests/backup-config-test.sh (temp home, fake pacman, sudo and bxrig). Not verified: a restore on a different machine.

    • backup snapshots (system snapshots). Btrfs root: snapper. setup [--home] installs snapper snap-pac (and grub-btrfs only when GRUB is in use), creates the root config (snapper -c root create-config /; --home adds /home), sets the timeline to 5 hourly, 7 daily, 2 weekly, 1 monthly, 0 yearly (snapper set-config TIMELINE_*), and enables snapper-timeline.timer and snapper-cleanup.timer (and grub-btrfsd.service). snap-pac takes a snapshot before and after every pacman transaction through its own hooks. Other filesystems: it installs Timeshift (rsync mode), which takes full copies and needs one visit to its window to pick a disk. list reads snapper --jsonout -c CONFIG list (snapshot 0, the live system, is left out); create [--description=T] is snapper create --description T -p; delete ID; changes ID is snapper status ID..0; restore ID PATH is snapper undochange ID..0 PATH (files changed since are replaced, files that did not exist then are removed, so the plan says so). There is no automatic whole-system rollback: rolling back a Btrfs root depends on your subvolume layout, so you boot the snapshot from the GRUB menu and follow the Arch wiki, or restore folders with restore. Everything that changes the system is a plan without --yes. Not verified on real Btrfs: the JSON shape of snapper --jsonout list (the parser accepts a bare array or an object holding one array), the timers, undochange. Tested with fakes in tests/backup-snapshots-test.sh.

    • backup data (your files, restic). A target is a place a restic repository lives: local (a path), nas (made by nas use, at ~/NAS/NAME/SHARE/PATH), sftp (sftp:user@host:/path; port as sftp:-p N user@host:/path), rest (rest:URL), s3 (s3:ENDPOINT/BUCKET/PATH, AWS when no endpoint; works for DigitalOcean Spaces, Wasabi, MinIO), b2 (b2:BUCKET:PATH), azure (azure:CONTAINER:/PATH), gs (gs:BUCKET:/PATH, with GOOGLE_PROJECT_ID and GOOGLE_APPLICATION_CREDENTIALS as the project and the service-account file) and rclone (rclone:REMOTE:PATH; FTP and any rclone service). The environment variable names (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_DEFAULT_REGION, B2_ACCOUNT_ID, B2_ACCOUNT_KEY, AZURE_ACCOUNT_NAME, AZURE_ACCOUNT_KEY, RESTIC_REST_USERNAME, RESTIC_REST_PASSWORD) and the address forms were read from restic's own documentation; the flags used (-r via RESTIC_REPOSITORY, backup --tag --exclude --exclude-caches --one-file-system, forget --keep-daily|weekly|monthly --prune, snapshots --json, ls --json, restore --target --include, check --read-data-subset) from the installed restic 0.19.1.

      • Keys go straight to the keyring (target add ... --ask-keys, typed hidden, or --keys-file with KEY=VALUE lines) as BXRIG_BACKUP_<TARGET>_<KEY>; the repository password is generated at init (24 random bytes, hex) and kept as BXRIG_BACKUP_<TARGET>_PASSWORD, with a reminder that losing it loses the backups. restic is started with these in its environment, never on a command line, and no key is written to backup.json.

    14.1 Install

    bootstrap/install.sh [--yes] [--dry-run] is the one install command. It prints the plan, asks one Proceed? [Y/n] at a terminal (without a terminal it needs --yes, else exit 2; --dry-run exits 0), then runs, in order: packages with yay and Rust, toolchains (mvm, bvm, BoxLang, nvm and Node, MatchBox), the bxrig binary, and the core apps (bxrig profile-install core --yes). External installer scripts run without a gate (section 2, rule 8). MatchBox (decided 2026-11-18, replaces the S3 build of the branch head): the toolchains stage installs MatchBox through mvm. Stable by default: mvm install latest, mvm use latest, only when no MatchBox is installed (a re-run leaves an installed one alone). --snapshot or BXRIG_MATCHBOX_CHANNEL=snapshot: mvm install snapshot, mvm use snapshot on every run (mvm skips an unchanged build). --matchbox-branch REF [--matchbox-repo OWNER/NAME] (BXRIG_MATCHBOX_BRANCH, BXRIG_MATCHBOX_REPO; the default repo is toolchain.matchbox.repo, the default branch of the alias --matchbox-from-source is toolchain.matchbox.ref, bxrig): git clone --depth 1 --branch REF, cargo build --release --features bif-tui, installed as $BXRIG_HOME/matchbox/bin/matchbox` with `build.info` (repo, branch, commit, source); it is first on the installer's PATH (never replaces mvm's MatchBox) and is rebuilt only when the repo, the branch or the remote head (`git ls-remote`, unreadable counts as moved) changed. Choosing `--snapshot` removes an earlier branch build; no option leaves it. REF `^[A-Za-z0-9._/@+-]+$ (no leading dash, no .., no leading or trailing slash) and OWNER/NAME are validated, invalid is exit 2, --snapshot with a branch is exit 2, and values reach git only as argv items.     • The System panel's Tasks tab and the bar share the failure count through noctalia.state (taskFailures); the bar reads scheduler --json with the updates every 10 minutes and draws a red dot while a task fails.
    • doctor --dev has a scheduler row (installed, no task failing); init has an optional scheduler step.

    Calendar (decided with the owner 2026-11-22)

    • bxrig calendar keeps calendars on this machine with vdirsyncer: an iCal address (read only, collections = null, webcal:// fetched as https://) or Google Calendar (google_calendar storage, collections discovered, OAuth on the first sync in a terminal). The user's own vdirsyncer config is never touched: BxRig writes ~/.config/bxrig/vdirsyncer/config (mode 600, it holds the Google client secret) and passes it as VDIRSYNCER_CONFIG. The registry is ~/.config/bxrig/calendars.json; the events are .ics files in ~/.local/share/bxrig/calendars/NAME.
    • calendar agenda reads those files with bxrig.Ical (pure: VEVENT, all-day dates, UTC times moved by date +%z, TZID and floating times as local, DURATION, RRULE DAILY/WEEKLY with BYDAY/MONTHLY/YEARLY with INTERVAL, COUNT, UNTIL, EXDATE, cancelled events left out).
    • bxrig remind TEXT --at|--in keeps reminders in ~/.config/bxrig/reminders.json; remind due shows the ones whose time has come as critical notices, once each.
    • The scheduler owns the timing: calendar-sync every 15 minutes and reminders every minute, added by the first calendar or reminder when the scheduler is installed, and by scheduler install when calendars or reminders exist. Scheduler.upsert never adds a task twice.
    • The Clock panel shows the agenda of today and tomorrow and the reminders still to come under the world clocks, with a check button per reminder.

    Launcher (decided with the owner 2026-11-22)

    • bxrig launcher makes Vicinae BxRig's launcher. setup is a plan until --yes: runner set vicinae and runner menu-set vicinae, the theme written and selected with vicinae theme set bxrig, the script commands written, and vicinae server started when vicinae ping fails. Vicinae's settings.json (JSONC, the user's) is never edited.
    • The theme is a generated file of theme set like the others: ~/.local/share/vicinae/themes/bxrig.toml (meta version 1, name, description, variant; colour keys only from Vicinae's theme parser's RECOGNIZED_KEYS). Vicinae watches the folder; theme set selects it again only while Vicinae is the launcher.
    • Script commands are ~/.local/share/vicinae/scripts/bxrig/*.sh, rewritten by launcher scripts --yes; a file BxRig no longer offers is deleted, other folders are not touched. Each sets BXRIG to this BxRig (BXRIG_SELF) and runs one command.
    • launcher files [QUERY] opens vicinae://launch/files/search with fallbackText. The Vicinae menu uses vicinae dmenu --placeholder (it has no --prompt).

    13.67 BoxLang agents: ai agents (decided with the owner 2026-11-24)

    bx-agents has a full command line (bxAgents, every verb on one project: the current folder or --projectRoot), so BxRig does not repeat it (AiAgentHub.bx). It adds only what bx-agents leaves to the machine. Where things live is bx-agents' own convention: an agent's data in ~/.bxagents/<name> (outside the project, so a build never replaces it), the person's settings in ~/.bxagents/Agent.yml. BxRig keeps its list in ~/.config/bxrig/agents.json (root, default, entries: [ { path, port, added } ]).

    CommandDoes
    ai agents [list]the projects: every folder of the projects folder with an Agent.yml or Agent.bx, then the ones added by path; name (the top-level name: of Agent.yml, else the folder), port, running, default
    ai agents install\|update [--snapshot\|--stable] [--yes] [--dry-run]bx-module install bx-agents@snapshot (the default for now), or @VERSION for --stable: the newest ForgeBox version without snapshot (exit 4 while there is none). Then /tmp/boxlang-jars is deleted, always, and the bxrig profile written. update also restarts the agents that run. Plan without --yes
    ai agents new NAME [flags]bxAgents new NAME [flags] in the projects folder, the terminal handed over (its own wizard). The name: letters, digits, - and _, not a command word, not taken
    ai agents NAME VERB [args]bxAgents VERB --projectRoot=PROJECT [args], exactly as typed (from the raw arguments), the terminal handed over, its exit code. Its flags are not checked against cli.json
    ai agents start\|stop\|status NAMEthe user unit bxrig-agent-NAME.service
    ai agents open NAME / default [NAME]its web page (xdg-open, only while it runs) / the default agent (for the keyboard shortcut, PR 11b)
    ai agents dir [PATH] / add PATH / forget NAME [--yes]the projects folder (BXRIG_AGENTS_DIR, else dir, else ~/Agents) / a project elsewhere (refused when its name is taken: the data folder is chosen by name) / out of the list, its unit removed, the project and its data kept
    ai agents profile [--off]the bxrig profile alone
    • Ports: from 8790, one per project path, kept; a freed one is used again.
    • The unit: ExecStartPre=bxAgents build --projectRoot=P --no-banner, then ExecStart=/bin/sh -c "cd .build && BOXLANG_HOME=P/.build/runtime exec boxlang-miniserver --port N --host 127.0.0.1", with Environment=BXRIG_SELF=PATH (BxRig's full path, for the agent's tools: a user service's PATH may not have ~/.local/bin) and Restart=on-failure. BOXLANG_HOME is set on the server's line only: set for the whole unit (as in PR 11) it reached the build step too, which then found no bx-agents module (measured, fixed in 11b). Not bxAgents serve: it starts the miniserver and exits 0 (measured), which systemd takes for the end of the service and stops the server with it. Running the miniserver in .build with the miniserver.json the build wrote is what bx-agents' deploy targets do; the flags win over the file. WorkingDirectory is the project, because .build does not exist before the first build and systemd checks the folder first.
    • The jar cache: BoxLang copies module jars to java.io.tmpdir/boxlang-jars (DynamicClassLoader.copyJarsToTemp, BL-2629) named by path and modification time, and reuses a copy that exists. bx-module install keeps the zip's 1980 dates, so a reinstalled jar would load the old copy (measured: NoMethodException on a method the new jar has). It is deleted after every install (BXRIG_BOXLANG_JARS names another folder).
    • Test hooks: BXRIG_BXAGENTS (the bxAgents launcher, else BOXLANG_HOME/bin/bxAgents, else the PATH), BXRIG_MINISERVER (boxlang-miniserver, else the PATH), BXRIG_FORGEBOX_API (default https://forgebox.io/api/v1).
    • The bxrig profile: in ~/.bxagents/Agent.yml, a marked block (# >>> BxRig local AI ..., # <<< BxRig local AI <<<) with profiles.bxrig = { description, provider: openai-compatible, model: ACTIVE, options.baseURL: BASE/v1 }. bx-agents layers that file over every agent at build and at start (SettingsLayers), mappings by key, so an agent uses BxRig's model with profile: bxrig. A file with a profiles: of its own is not rewritten (the lines to add are given). ai models use rewrites the block when it is there; it is never added unasked. Checked for real: profile:, providers.openai-compatible.options and a top-level options all reach the local server, from invoke and from the served app.
    • Control Center: ai-boxlang (BoxLang agents, after Agents): ai agents --json; Enter the chat in a new terminal (setsid -f TERMINAL bxrig ai agents NAME chat), o web page, s start or stop, d default, l journalctl --user -u UNIT, i install or update. Bar: the Agents panel's BoxLang tab (boxlang.luau).
    • Java's home is not $HOME: bx-agents reads user.home, which comes from the account, so a test that changes HOME sets BXAGENTS_USER_CONFIG too.
    • Tests: tests/ai_agents_test.bxs (pure), tests/ai-agents-test.sh (fake bx-module, bxAgents, systemctl, curl and xdg-open). Checked for real against bx-agents 1.0.0-snapshot (2026-11-24) and BoxLang 1.20.0-snapshot: install, new, build, invoke and models list through the pass-through, the unit's two commands, the served /__bxagents/invoke answering through the bxrig profile. Not yet on a real desktop: the interactive chat hand-over, a real systemd user session, the terminal opened from the Control Center and the bar tab in Noctalia.

    13.68 Boxy, the desktop assistant (decided with the owner 2026-11-25)

    Boxy is a bx-agents project BxRig ships as a template (templates/agents/boxy/: Agent.bx, instructions.md, tools/BxRig.bx, packed with the binary). It is an Agent.bx (the class form) because a class can add bx-ai's approval step; an Agent.yml can not for its own tools.

    CommandDoes
    ai agents setup [--no-start] [--yes] [--dry-run]writes the template to PROJECTS/Boxy (refused when Boxy or the folder exists), writes the bxrig profile when it is missing, makes Boxy the default agent and starts it. Plan without --yes. Named setup, not boxy: words are compared without case, so boxy would have shadowed bxrig ai agents Boxy VERB
    ai agents chat [NAME] [--window]bxAgents chat --projectRoot=P, plus --connect=http://127.0.0.1:PORT when the agent runs (one agent for the chat, the web page and the bar); --window opens a terminal (Ai.terminal()) that runs it, for the shortcut. No NAME: the default agent
    ai agents open [NAME]as before; no NAME: the default agent
    ai agents ask TEXT [--agent=N] [--thread=T]POST /__bxagents/invoke { input, threadId } (the field is input: a body with message reaches the model as an empty question) to the running agent; { answer, thread, pending: [ { tool, args } ] }. The thread is bxrig- and 12 hex digits unless given
    ai agents approve\|reject THREAD [--agent=N] [--session]POST /__bxagents/resume { threadId, decision } (approve, approve_session, reject); the stream is read for the tools that ran (tool frames with status: ok), the answer (chunk frames: choices[1].delta.content) and what it waits for next (suspended)
    ai agents skills [NAME] [show\|approve\|remove SKILL] [--all] [--yes]the skills the agent saved in ~/.bxagents/NAME/skills/*/SKILL.md (name and description from the front matter). Reviewed means the SHA of SKILL.md matches the one kept in agents.json reviewed when you approved: saving over it flags it again. A flagged skill stays active (owner's choice). remove deletes the folder, plan first
    • The approval step: Agent.bx calls withCheckpointer( aiMemory( memory: "cache" ) ) before withMiddleware( new HumanInTheLoopMiddleware( toolsRequiringApproval: NEEDS_OK, mode: "web" ) ); without the checkpointer first the class does not load (measured: "HumanInTheLoopMiddleware is attached to mode web ... but the agent has no checkpointer"). Verified for real: the run pauses before the tool runs, /pending names it, /resume approve runs it, reject does not.
    • The tools: 36 @AITool functions in tools/BxRig.bx, each bxrig ARGS --json through systemExecute, BXRIG_SELF else bxrig; the model gets the envelope's data as JSON (cut at 6000 characters) or what failed. The 19 that change something are in NEEDS_OK and pass --yes where the command asks for it (the approval was the plan). Argument descriptions come from the doc comment (@arg text); no argument is called name.
    • Model: the bxrig profile (configure() returns { profile: "bxrig" }), which now sets options.timeout: 300 (measured: Qwen3.5 4B on 4 CPU cores took over 90 s, bx-ai's default, for its first answer with the 36 tools). Measured on 2026-11-25 against the served Boxy: Qwen3.5 0.8B listed the themes, asked for night_light_set {state: on} and reminder_add {stretch, 30m}, and once proposed an unasked brightness_set (held by the approval); Qwen3.5 4B listed the 24 themes from theme_list and asked for night_light_set {state: on}.
    • Shortcuts: agent-chat Super+Period (ai agents chat --window), agent-web Super+Shift+Period (ai agents open), both styles, Hyprland.
    • Setup: the wizard's AI page asks boxy (now by default, later); init then runs ai agents install --yes and ai agents setup --yes, both optional, after ai-setup.
    • Bar: the Agents panel's Boxy tab (boxy.luau): the default agent with Start or Stop, Chat, Web, Ask with Approve and Reject, the count of skills to review with Review; Make Boxy when there is none.
    • Tests: tests/ai_agents_test.bxs and tests/ai-agents-test.sh (the template copied as is; chat stopped and running; --window; ask, approve, reject and --session against a fake agent API; the skill review), tests/init_plan_test.bxs (the two steps and their order). Checked for real against bx-agents 1.0.0-snapshot and BoxLang 1.20.0-snapshot: Boxy made from the template, built and served by its unit, its read-only tools answering from real bxrig output, changing ones waiting; ask, approve and reject against a served agent. Not yet on a real desktop: the chat in a terminal from the shortcut, a real systemd user session and the bar tab in Noctalia.
