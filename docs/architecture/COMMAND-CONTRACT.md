# BxRig command contract

Target (2026-11-09): Hyprland + Noctalia on CachyOS, KDE kept side by side; see plan.md section 19. `setup` is the headline command.

Status (2026-11-15): **built.** This file started as the proposal and became the design record; sections 1 to 12 are the rules and the first build, section 13 onward holds one decision section per feature, 14 the installer and the wizard. Where a sentence here and the code disagree, the code wins: `docs/reference/cli.json` is the command registry (96 commands and their flags, usage and examples), `docs/reference/commands.md` is generated from it, and `bxrig help NAME` prints the same text. The legacy tree in `artifacts/legacy/original/` is the v0.10.0 source, kept as a feature reference and never modified.

## 1. Grammar

```
bxrig <command> [subcommand] [args...] [--yes] [--dry-run] [--json] [--quiet] [--force]
```

- A command is one word from `docs/reference/cli.json` (`setup`, `keys`, `menu`, `record`, `browser`, ...); its subcommands and positional arguments are in its usage lines. Groups in the reference (Start here, Install, Desktop, Look, System, Develop, Tools) only organise the page.
- Mutating verbs (`install`, `apply`, `remove`, `restore`, `enable`, `disable`, `set`, ...) need `--yes`; read-only ones (`list`, `show`, `status`, `plan`, `doctor`) never do.
- Flags are checked against the registry before anything runs: a flag the command does not list is a usage error (exit 2, the usage line is printed); `secrets run` passes everything after its own flags through. An unknown command is exit 2 too.
- `CLIGetArgs()` puts flags in `args.options` and the words in `args.positionals`; a flag with a value is written `--name=value` (the form `--name value` is a flag plus a positional on MatchBox).

## 2. Mutation rules (apply to every mutating verb)

1. No `--yes`: print the exact plan, change nothing, exit 2.
2. `--dry-run` with `--yes`: print the exact plan, change nothing, exit 0.
3. Preflight everything before the first mutation. A preflight failure means zero changes.
4. Never escalate privilege silently. `sudo` is only called for pacman steps shown in the plan.
5. Never run AUR builds as root (exit 4).
6. Every config file touched goes through the config service (backup, atomic replace, journal). No direct writes.
7. Output lists succeeded and failed items separately. No rollback is promised across pacman and yay.
8. External installer scripts (bvm, mvm, `toolchain node`'s nvm, catalog `source: script`) are downloaded to a temp file, their url and sha256 are printed, and they run as the normal user (never root) with no confirmation gate and no flag: the typed `EXECUTE` and `--allow-external-scripts` were removed on 2026-11-10 (owner: running them is the point of the command). Decision 2026-11-09: no checksum pinning for these scripts.
9. Subprocesses are launched with argument arrays, never through a shell string. The one place that starts a process is `util/Proc`; the few `sh -c` wrappers pass every value as a positional argument (`detach`, recording, the pull-down shells).
10. The plan, dry-run and run protocol is one class, `util/Mutation`, reached through `Out.plan( ... )`: no `--yes` prints "Plan: TITLE", the extra lines and "Nothing was changed. Add --yes to apply." (exit 2); `--dry-run` prints "Dry run: TITLE" and the same lines (exit 0); the first failing step ends the run (exit 6). A ratchet in `tests/dry-test.sh` forbids hand-written plan footers.
11. Documented exceptions to `--yes`: a command that changes only your own settings or starts or stops a program acts at once and takes `--dry-run` (themes, `appearance`, `time format`, `display`, `notify`, `tiling`, `runner set`, `layout`, `record`, `webcam`, `window`, `browser private`, `files here`, `dictation toggle`). Anything that installs packages, writes system files or changes login behaviour always needs `--yes`.

## 3. Exit codes

| Code | Meaning | Example |
|---|---|---|
| 0 | Success or no-op | already installed, or `--dry-run` |
| 1 | Check negative | `package-status` says missing |
| 2 | Usage error or missing confirmation | no `--yes`, unknown flag |
| 3 | Timeout, or item unavailable | pacman lookup timed out, package not in any repo |
| 4 | Precondition failed | root with AUR, not Arch, Java missing, not KDE where required |
| 5 | Official (pacman) phase failed | |
| 6 | AUR (yay) phase failed | |
| 7 | Partial success | some items done, some failed; `--json` lists both |
| 8 | Config conflict | drift detected, symlink or special file at target, concurrent run lock |
| 9 | Internal error | bug, unexpected exception (`Application.bx` `onError` prints it and exits 9) |
| 10 | An update is available | `update check` only |

The codes are frozen. `tests/cli-contract-test.sh` and the per-command tests check them; a bad name is exit 2 everywhere (it was 4 in some commands before the `Names` helper); an unknown command or flag is exit 2.

**Names in code.** `src/bxrig/util/Exit.bx` names every code: `ok` 0, `negative` 1, `usage` and `plan` 2, `timeout` 3, `precondition` 4, `official` 5, `failed` 6, `partial` 7, `conflict` 8, `internal` 9, `update` 10. `Cli.say`, `Cli.fail`, `Out.say` and `Out.fail` take a name or a number; an unknown name throws. Command classes write the name (`variables.out.say( "precondition", ... )`, `CLIExit( xit.usage() )`, `return new bxrig.Exit().ok();`), so a typo cannot turn into a wrong exit code. The numbers on the wire are the table above. `tests/dry-test.sh` fails on a bare number as the code argument of `say`/`fail` and on `CLIExit( N )` in `Main.bx` (130, Ctrl+C, is the exception).

## 4. `--json`

With `--json` a command prints one JSON object on stdout and no human text (`Cli.envelope`):

```json
{
  "schema": 1,
  "command": "profile install",
  "version": "0.11.0-dev",
  "ok": false,
  "exit": 7,
  "dry_run": false,
  "data": { "done": [], "failed": [], "skipped": [] },
  "warnings": []
}
```

`data` is different for every command (the package commands put `would_install`, `done`, `failed` and `skipped` there, section 11); `ok` is true when `exit` is 0. A plan is `exit` 2 with the plan in `data`; a dry run is `exit` 0 with `dry_run` true.

## 5. Catalog (single source of truth)

The catalog is `catalog/apps.json` (schema 4, 349 apps today, version in `catalog_version`: what each app is) plus one install file per distribution, `catalog/install/{arch,suse,debian,ubuntu}.json` (how to install it there; see "Distributions"), packed into the binary as a resource (`src/resources/catalog`). It started as the legacy `apps.json` (482 entries) and replaced the hardcoded lists. The findings below are the 2026-11-09 audit of that legacy data and are kept as the record of why the catalog looks as it does.

Entry schema (legacy fields kept, new fields marked):

| Field | Notes |
|---|---|
| `id`, `name`, `kind` (`desktop` `tui` `web`), `category`, `description` | as legacy |
| `source` (`pacman` `aur` `pkgbuild` `script` `manual` `web`), `target` | package name, or URL for web and script |
| `pkgbuild` source: `repo`, `path`, `ref` | Build with `makepkg` as the normal user from a PKGBUILD in a public git repo, pinned to a full 40-character commit (`catalog check` rejects anything else), then install the result with pacman. Used for desktop apps packaged in `omacom/omarchy-pkgs`. The PKGBUILD is shown before it is built. |
| `check` (for `script`) | argv array that exits 0 when installed, for example `["command","-v","pi"]` |
| `default` | base tier flag |
| `source_status`, `source_confirmed` | legacy provenance flags, kept |
| `profiles` (new) | list of profile ids |
| `deps` (new) | other catalog ids |
| `check` (new) | optional post-install check, argv array |
| `verified_on` (new) | date the target was confirmed against real repos |

Findings from the legacy data (historical, decisions recorded 2026-11-09):

- **Unverified sources.** 176 entries are `source: manual` (95 tui, 81 desktop). Their package names are unverified. Proposal: a CI job that checks every `pacman`/`aur` target against real repos (Arch container, AUR RPC) and fails on unknown names. `manual` entries stay installable only by explicit user action.
- **Default list mismatch.** 61 flagged default (29 pacman, 18 aur, 14 web). `app-profile.json` `base` lists 46. 20 defaults are not in that base list (for example `ark dolphin dolphin-plugins kio-extras rclone fuse3 sshfs nfs-utils cifs-utils podman-desktop tabby beekeeper-studio google-docs google-sheets google-slides kompare filelight ffmpegthumbs kdegraphics-thumbnailers kimageformats`). 5 base entries are not flagged default (`dbeaver filezilla krdc podman-tui rustdesk`). The 61 flags win. The 5 dropped base entries are `dbeaver` (pacman), `filezilla` (pacman), `krdc` (pacman), `rustdesk` (aur) and `podman-tui` (manual). Pending: keep them as curated (not default), or re-flag any as default.
- **Browsers.** `brave` is `aur` (`brave-bin`) and default. A fresh default install therefore needs yay on day one. Decision: bootstrap installs yay only if it is not already present.
- **Preserve list.** Legacy `preserve` (CachyOS, KDE Plasma, Hyprland, Noctalia, existing user configs) becomes enforced rules, not just text.

Named profiles keep the existing four (`core jvm containers terminal`) and are expressed as catalog `profiles` tags. Later profiles (`web backend ai ops desktop full`) are added only after package names are verified.

Ship vs embed (pending confirmation): the default catalog is embedded in the binary at build time, so there is one file to ship and it always matches the code. An optional `~/.config/bxrig/catalog.json` adds entries or sets `default`/`profiles` on existing ids. It is validated against the same schema and can never delete or replace an embedded entry's `target`, so a bad override cannot redirect an install.

## 6. State and config layout

```
~/.config/bxrig/            same root as legacy
  bxrig.json                global settings
  catalog.json                optional user additions (merge-only)
  ai.json menu.json shortcuts.json ...   one file per feature, as legacy
~/.local/state/bxrig/
  journal/                    one record per apply: files, hashes, backup paths
  backups/                    backups, indexed by the journal
  lock                        single-writer lock
```

`config list|diff|apply|restore` work from the journal, so restore needs only an id. Retention default: keep the last 20 per file. Open: this applies to the user's config files that BxRig writes, not to the legacy source tree.

## 7. Test contract

- A snapshot test freezes `bxrig help`, the exit-code table and the `--json` schema.
- Every mutating verb needs these cases: success, no-op, invalid input, dependency failure, privilege rejection, partial failure, recovery.
- Real-system cases run in `tests/arch/` (non-root, real pacman). Cases needing KDE, Wayland or hardware are marked `manual` and tracked in the acceptance log.

## 8. Catalog check, validation and reporting

`bxrig catalog check [--json] [--online]` plus a CI job that runs it in the Arch container.

**Offline validation (always, no network):** schema version; unique ids; enums for `kind`/`source`; `web` targets are https with no credentials or control characters; package targets match `^[a-zA-Z0-9@._+-]+$`; `default` entries have a non-`manual` source; `profiles` and `deps` reference existing ids; no dependency cycles.

**Online verification (`--online`, CI):** every `pacman` target must resolve with `pacman -Si` (or `-Sg` for groups); every `aur` target must resolve through the AUR RPC (`/rpc/v5/info`); `manual` targets are probed against both and reported as promotable. Results are stored per entry as `verified_on` and a status: `ok`, `moved` (listed source is wrong but another source has it), `missing`, `unverified`.

**Reporting:** a table by status and source for the console, `--json` for tools, and a markdown report in the CI step summary and artifact. Policy: `missing` entries with `default: true` fail CI; `missing` non-default entries are warnings listed in the report; `moved` entries are warnings with the suggested fix.

**First measurement (2026-11-09, stock Arch core/extra only, so CachyOS repos and multilib are not covered):**

| Check | Result |
|---|---|
| `pacman` targets (118) | 111 resolve, 7 do not: 5 exist in AUR (`git-cola insomnia localsend ulauncher wlogout`), 2 found nowhere (`intellij-idea-community-edition`, `swww`) |
| `aur` targets (64) | 40 resolve in AUR, 11 are now official (`doggo impala nwg-dock-hyprland opencode podman-desktop rio spotify-launcher superfile television warehouse zenmap`), 13 found nowhere (`beeper ctop dbgate espanso grokbot herder inshellisense notion-desktop pi-agent tmog todoist upnote zap-whatsapp`) |
| `manual` targets (176) | 93 are official packages today (promotable, for example `jq ripgrep-all tmux kitty starship terraform kubectl`), 83 are not |

The check must also run against the CachyOS repos on a real CachyOS machine before any `missing` entry is removed.

## 11. Package commands on the catalog (B2, decided 2026-11-09)

Applies to `plan`, `install-plan`, `install`, `optional-*`, `profile-*`, `package-status`, `package-source`. All read the embedded catalog (schema 3). Hardcoded lists in `Main.bx` go away.

### Selection

```
bxrig install                       # tier default
bxrig install ID [ID...]            # exactly these apps
bxrig install --profile=NAME        # a profile
bxrig install --optional            # default tier plus optional tier
```

- Naming an app is enough. There is **no `--aur` flag**: anything in the catalog installs from its `source` (`pacman`, `aur`, `pkgbuild`, `web`).
- Unknown id: usage error (exit 2), nothing runs.
- Skip reasons: `optional` (not selected), `wrong_shell` and `unresolved` (catalog has no installable source yet; a named `unresolved` app is reported `failed`, exit 3).
- Already installed apps are `skipped` with reason `installed`.
- Section 2 still applies: no `--yes` prints the plan and exits 2; `--dry-run --yes` prints it and exits 0. AUR and `pkgbuild` builds never run as root (exit 4).
- Profiles live in the catalog (0.3.0): a top-level `profiles` list and, per app, a map profile id to `default`/`optional`. `--profile=NAME` installs the profile's `default` members; `--optional` adds its `optional` ones. See `catalog/README.md`.
- Shells: an app may carry `shells` (`hyprland`, `plasma`). The running shell comes from `XDG_CURRENT_DESKTOP`, overridable with `--shell=hyprland|plasma|all`. Non-matching apps are `skipped: wrong_shell`; a named app still installs.

### Per-source steps

| source | step |
|---|---|
| `pacman` | one `pacman -S --needed` call for all pacman apps (sudo shown in the plan) |
| `aur` | AUR helper (yay) as the normal user, apps one at a time |
| `pkgbuild` | PKGBUILD shown, `makepkg` as the normal user, result installed with pacman |
| `web` | a `.desktop` launcher in `~/.local/share/applications/bxrig-<id>.desktop` running `brave --app=URL` (written atomically, no package). The resolver adds `brave` to the plan when a web app is selected and brave is not installed. |

### Result shape (`--json`, inside the section 4 envelope)

`data` for `plan`, `install-plan` and `install`:

```json
{
  "selection": { "mode": "default|ids|profile|optional", "ids": [], "profile": null },
  "would_install": [ { "id": "git", "source": "pacman", "targets": ["git"] } ],
  "done":    [ { "id": "git", "source": "pacman" } ],
  "failed":  [ { "id": "docker", "source": "pacman", "error": "target not found" } ],
  "skipped": [ { "id": "jq", "reason": "optional" } ]
}
```

- `plan` and `--dry-run` fill `would_install` and leave `done`/`failed` empty. A real run fills `done`/`failed` and leaves `would_install` empty.
- Exit: 0 all done or nothing to do; 5 pacman phase failed, 6 AUR/pkgbuild phase failed (only when nothing succeeded); 7 some done and some failed.
- `package-status ID` exits 0 when installed, 1 when missing; `data` is `{ "id", "source", "installed": true|false }`.
- `package-source ID` prints `{ "id", "source", "targets", "tier", "group" }`.

Human output is the same lists, one app per line with its source.

## 13. Desktop setup (decided with the owner 2026-11-09 and 2026-11-10; all built)

Builds on sections 2 to 4 (mutation rules, exit codes, `--json`), the config service (section 6) and the `Installer` (argument arrays, `done` / `failed` / `skipped`). Hyprland with Noctalia is installed beside KDE Plasma; KDE is never removed or reconfigured except what `--keys` hands over, which is backed up first.

### 13.1 Commands

```
bxrig setup hyprland [--yes] [--dry-run] [--json]    packages, images, starter configs, shortcut files
bxrig setup plasma   [--yes] [--dry-run] [--json]    HyprKwin tiling on KDE Plasma
bxrig setup plasma --keys | --undo-keys              hand Plasma's clashing keys over / back
bxrig setup hyprland --terminal=ghostty|kitty|alacritty|foot|konsole   Super+Enter terminal (ghostty default)
bxrig setup hyprland --layout=dwindle|master|scrolling|floating        default window layout in the starter hyprland.lua (dwindle default)
bxrig setup hyprland --workspaces=N --natural-scroll --layouts=us-intl,es --theme=dark|light|auto --wallpaper=box|grid|aurora|minimal   starter choices (defaults: 2, off, us, dark, box); two or more keyboard layouts switch with Alt+Shift
bxrig setup terminal [--default=ghostty] [--also=kitty,foot,...]       install terminals, starter configs with the Nerd Font
bxrig setup shell [--shell=zsh|fish|bash]                              Starship + shell init, login shell (zsh default)
bxrig setup xremap [--build=hypr|kde] [--yes]        Cmd-style keys: AUR package, input access, user service
bxrig setup undo hyprland|plasma|xremap [--yes]      remove only what setup added
bxrig setup status [--json]
bxrig tiling on|off|status                           HyprKwin inside Plasma, no logout
bxrig keys show | search TEXT | run ID | style [traditional|mac] | set ID KEYS | reset ID | conflicts | sheet | render xremap|hyprland|plasma | check | apply [--yes] [--dry-run] [--force]   (the full usage is in cli.json)
bxrig assets list | install [--yes] [--dry-run]
bxrig session show | set hyprland|plasma [--yes] [--dry-run]
bxrig runner list | show | doctor | launch | select JSON | set P | menu-set P | launcher-command P JSON | menu-command P JSON   the launcher abstraction (13.9)
```

- Every target runs, re-runs and undoes on its own; a re-run changes nothing when everything is in place. No `--yes` prints the plan (exit 2); `--dry-run` exits 0. Results as `install`: `done` / `failed` / `skipped`, exits 0, 2, 4 (precondition: root, wrong OS or CPU, no sudo, no Plasma, unsupported Plasma, X11, nothing to undo, session not installed), 5 (the pacman step failed), 6 (another step failed with nothing done), 7 (a step failed after earlier ones were done; later steps are skipped), 8 (config drift or lock). Never run as root: sudo is used only for the steps shown in the plan. `--json` is always one envelope on stdout (the config service has a quiet mode for that). **A failed step says why** (2026-11-17): its `failed` entry carries `command` (the argv that failed) and `output` (the last five lines of what it printed, at most 800 characters), and the text report prints them under the `Failed:` line (`  command: ...`, `  | line`); `bxrig init` does the same for its steps. **systemd steps are skipped where systemd is not running** (no `/run/systemd/system`: a container or a chroot; `BXRIG_SYSTEMD_RUN_DIR` replaces the path in tests): the step is listed in `skipped` with the reason and the command to run on a real system, the plan carries a warning, and the run is not a failure.
- **Exception to `--yes`:** `tiling on|off` acts at once (a reversible user setting meant to sit behind a shortcut). `status` exits 0 on, 1 off, 4 not installed.

### 13.2 `setup plasma` (HyprKwin)

HyprKwin (`DGBooth/HyprKwin`) is a KWin script with Hyprland-style layouts and keys. It needs Plasma 6.6 or 6.8 on Wayland (6.7 warns, older or X11 exit 4). It is fetched **pinned to a full commit** (v1.2.0, `31abb63`, same rule as PKGBUILDs) into a temp directory and installed with its own `tools/install.sh` as the normal user, which backs up every global shortcut first. Plasma's keys stay Plasma's unless `--keys` (runs `tools/hyprkwin-shortcuts.py apply`; `--undo-keys` restores). The animations effect needs one logout. `setup undo plasma` runs HyprKwin's uninstall. `tiling on|off` sets `hyprkwinEnabled` in `kwinrc` `[Plugins]` and asks KWin to reconfigure over D-Bus (`off` also unloads the script).

### 13.3 `setup hyprland`

Preconditions (exit 4): not root, pacman, CachyOS or Arch, x86_64, sudo. Steps, in order:

1. `packages`: the missing ones of 17 official packages in one `sudo pacman -S --needed` call: `hyprland`, native `noctalia`, `uwsm`, `hyprlock`, `xdg-desktop-portal-hyprland`, `hyprpolkitagent`, `qt6ct`, `nwg-look`, `hyprpicker`, `grim`, `slurp`, `wl-clipboard`, `brightnessctl`, `kitty`, `adw-gtk-theme`, `noto-fonts`, `noto-fonts-emoji`. Individual packages, never the CachyOS meta-package `cachyos-hypr-noctalia` (it conflicts with `cachyos-desktop-settings`, which the KDE session may rely on). Noctalia is the native `noctalia` package; `noctalia-shell` + `noctalia-qs` are a different Quickshell-based variant that conflicts with `quickshell` (a warning, not an error, if installed). The packages added are remembered (`$XDG_STATE/bxrig/setup-hyprland.json`, mode 600) so `setup undo hyprland` runs `sudo pacman -Rs` on exactly those.
2. `images`: the logo and wallpapers (13.6), missing ones only.
3. `starter`: the Noctalia config and palette, and a first `hyprland.lua` (13.5).
4. `keys`: the shared shortcut files (13.4).

### 13.4 Shortcuts, `keys` and `setup xremap`

One embedded table (`Shortcuts.bx`) holds the shortcuts and is rendered per target. The same keys work on Hyprland and Plasma [owner]:

| Part | Hyprland | Plasma |
|---|---|---|
| Tiling and workspace keys | Hyprland's own keys | HyprKwin (same defaults) |
| Cmd-style keys: Super+C, V, X, A in both styles; the rest and Super+Tab in the Mac style | xremap | xremap |
| Logout to the login screen, Super+Shift+Q | `hl.bind(... "uwsm stop")` | `kglobalshortcutsrc` `[ksmserver] Log Out` via kwriteconfig6 |

Two key styles share the table (decided with the owner 2026-11-14, `SHORTCUTS-DECISIONS.md`): **Traditional** (classic Super-key tiling keys) and **Mac** (Cmd-style keys). Every row has a key per style; every Hyprland bind (the starter file's and the module's) is a row, so `keys show`, `keys sheet`, `keys set` and `keys conflicts` see all of them. The style, the keyboard (`pc` or `apple`) and the Alt/Win swap are in `~/.config/bxrig/keystyle.json`, set with `keys style` (the wizard asks for the keyboard when Mac keys are on). The swap is a `modmap` in the xremap config (left Alt and left Win exchanged); it is active only for the Mac style on a PC keyboard. `keys conflicts` reports bindings that share a combo, bindings on a key xremap rewrites (only the remaps of the style that is on count) and clashes with the user's own `hl.bind` lines.

- xremap, one shared YAML: Super+C/V send Ctrl+C/V, and Ctrl+Shift+C/V in terminals (a class list in the table); Super+Tab is a plain Alt+Tab remap [owner], answered on Hyprland by Noctalia's window switcher (`noctalia msg window-switcher hold`).
- `keys render` prints a target's text (pure). `keys apply` writes `~/.config/xremap/config.yml`, `~/.config/hypr/bxrig.lua` and `~/.config/systemd/user/xremap.service` through the config service (backup, journal; `config list|diff|apply|restore` cover them) and sets Plasma's Log Out with kwriteconfig6 when present. `keys check` reports clean / missing / outdated / drifted per piece (exit 0 or 1); a changed file is never overwritten without `--force`.
- Since 2026-11-16 the table has 160 rows (19 xremap remaps, 17 unbound Control Center page rows, 124 bindings) and `keys conflicts` is clean in both styles. xremap is always installed and enabled: copy, paste, cut and select all are remaps in both styles, so the wizard no longer ties it to the Mac question. The Mac style on a PC keyboard also swaps Alt and Win in the same xremap file (`modmap`, left keys only). ### 13.9 `runner`: the launcher abstraction (port of the legacy `bxrig-runner`)

**Design (owner, 2026-11-10): BxRig is built on an abstraction so runners can be switched.** The rest of BxRig asks for two things and never names a launcher:

```
Runner.launch()                      open or toggle the launcher
Runner.select( prompt, entries )     show [ { label, icon } ] in a menu, return the chosen position (0 = cancelled)
```

**Super+Alt+Space (Hyprland, both key styles)** is bound once, in the managed `bxrig.lua`, to `bxrig runner launch` (falling back to `noctalia msg panel-toggle launcher` when the chosen launcher cannot run), so `runner set` changes what it opens without ever editing a keybinding. `Super+Space` opens the BxRig menu (`bxrig menu`, 13.16). Which launcher answers is a setting, recorded in `~/.config/bxrig/runner.json` (written atomically); the launcher and the menu provider are chosen separately. **The runner never changes a keybinding or a desktop file** (`doctor` ends with `Shortcut ownership: unchanged`). `set` and `menu-set` are user settings that act at once (no `--yes`), like `tiling`.

Providers are data in `RunnerProviders` (one descriptor each: `id`, `title`, `package`, `launch` argv, and `menu`: dmenu argv with `{prompt}`, `icons`, `returns`). Adding a launcher is adding one descriptor.

| Provider | Launch | Menu (dmenu mode) | Icons | Choice comes back as | Package |
|---|---|---|---|---|---|
| `noctalia` (default on Hyprland) | `noctalia msg panel-toggle launcher` | none | | | with Noctalia |
| `walker` | `walker` | `walker --dmenu` | no | label | Walker |
| `rofi` (default menu) | `rofi -show drun` | `rofi -dmenu -i -show-icons -format i -p` | yes | index | `rofi` |
| `fuzzel` | `fuzzel` | `fuzzel --dmenu --index --prompt` | yes | index | `fuzzel` |
| `wofi` | `wofi --show drun` | `wofi --dmenu --insensitive --prompt` | no | label | `wofi` |
| `vicinae` | `vicinae toggle` | `vicinae dmenu --prompt` | no | label | `vicinae-bin` (AUR) |
| `krunner` | `krunner` | none | | | with KDE |
| `system` | none (the desktop owns it) | none | | | |
| `custom` | your `custom_command` | none | | | |

`select` writes the labels (one per line, newlines inside a label become spaces) to a temporary file and runs the provider's command with it on stdin through `sh -c 'exec "$@" < "$f"'`. Providers that understand Rofi's extended dmenu protocol (`label` NUL `icon` US `name`) get icons; the others get plain labels. A non-zero exit, an empty answer, an unknown label or an index out of range is a cancel, never a wrong choice.

```
bxrig runner list | show | doctor | launch [--json]
bxrig runner set P | menu-set P
bxrig runner icon-theme NAME|auto                                          the icon theme Rofi and Fuzzel draw icons from (see below)
bxrig runner launcher-command P JSON_ARGV | menu-command P JSON_ARGV     JSON argument arrays, {prompt} allowed
bxrig runner select JSON_ENTRIES [--prompt=TEXT] [--json]                prints the 0-based index; exit 1 cancelled, 4 menu cannot run
```

Commands are JSON argument arrays, never shell strings (a string, an empty array or an empty part exits 4). `list` marks the current choice with `*` (`--json` adds each provider's title, package, icon support and answer format). `doctor` shows the commands and whether each executable is on PATH. `launch` starts the launcher detached (exit 4 for `system` or a missing program). The wizard offers Noctalia, Walker, Rofi, Fuzzel and Wofi; Vicinae, KRunner and `custom` work from the command line. `hyprrunner` was dropped (no package found, 2026-11-10). Fuzzel and Wofi flags are from their man pages.

**Icon theme (`IconTheme.bx`, `runner icon-theme NAME|auto`).** Rofi and Fuzzel draw the runner's icons from one icon theme, chosen in this order, each only when that theme folder exists (`~/.local/share/icons`, `~/.icons`, `/usr/share/icons`): `BXRIG_ICON_THEME`, `icon_theme` in `runner.json` (what `runner icon-theme NAME` writes; `auto` removes it; an uninstalled name exits 4), the GTK setting (`gtk-3.0` and `gtk-4.0` `settings.ini`, then `gsettings org.gnome.desktop.interface icon-theme`), then the first installed of Papirus, Adwaita, elementary-xfce, breeze, else hicolor. `theme set` writes it into `rofi.rasi` (`configuration { icon-theme: "NAME"; }`, which Rofi 2 honours inside an imported theme) and `fuzzel.ini` (`[main] icon-theme=NAME`), so apply a changed choice with `bxrig theme set`. Each section's icon is resolved against the theme at menu start with one `find`: the wanted name, its `-symbolic` twin, a few alternatives (`IconTheme.alternatives`), then `folder`, `application-x-executable` and `bxrig` (the app icon in the user's hicolor), so a theme that lacks a name never leaves a gap; when nothing resolves the row is shown without an icon. Tests: `tests/icon_theme_test.bxs`, `theme-test.sh`, `runner-test.sh`.

### 13.10 `db`: local databases and search engines as containers (port of the legacy `bxrig-db` and `bxrig-vector`)

```
bxrig db engines | list [--json]
bxrig db start ENGINE [--name N] [--port P] [--password-file FILE | --ask-password] [--yes] [--dry-run]    create, or start a stopped one; never replaces a container
bxrig db stop|status|logs ENGINE [--name N]
bxrig db remove ENGINE [--name N] [--keep-data] --yes              removes the container AND its data (volume and password file); --keep-data keeps the data
bxrig db info ENGINE [--name N] [--show-password]                  where it listens and how to connect (password masked by default)
bxrig db engine [podman|docker]                                    which engine runs them (podman by default, saved in ~/.config/bxrig/db.json)
bxrig db menu                                                      the control center, on the runner's menu provider (needs a terminal program)
```

Exit codes: 0 done, 2 usage or no `--yes` (the plan is printed; `--dry-run` exits 0), 4 precondition (no container engine, unknown or unsupported engine, bad name or port, `vm.max_map_count` too low), 6 the container command failed. `--json` gives the standard envelope.

**Bar plugin data.** `db list --json` rows are `{container, status (the engine's text), state (running, paused, created, exited), image, engine, name, port}`; `db info ENGINE --name N --show-password --json` returns `data.url`, the connection string the Developer bar plugin copies (`vm list --json` has `state`, `ports`, `url` per VM and `vm start|stop NAME` run them).

**Rules.** Services listen on `127.0.0.1` only. A container that exists is never replaced (a stopped one is started; a running one is left alone). Containers are named `bxrig-db-<engine>-<name>` (name defaults to `default`; letters, digits and hyphens) and labelled `io.bxrig.database=true`. Data lives in a **named volume** with the container's name, not a host folder (`db remove` deletes it together with the container and the password files, so the next start is a clean database; `--keep-data` keeps them, and starting the same name again then reuses the volume and its password): rootless containers cannot write to a bind-mounted folder as the image's own user (OpenSearch, Elasticsearch and Meilisearch run as non-root). **Choosing the password:** by default one is generated. `--password-file FILE` uses the first line of a file you made; `--ask-password` asks twice at the terminal without echo (`/dev/tty`, so it needs a terminal; the plan never prompts). A password is **never** a command-line value, so it cannot land in shell history or the process list. It must be 8 to 128 characters with no whitespace (OpenSearch also needs upper and lower case, a digit and a special character). It applies only when the container is created (the image sets it on first start of the data volume): a second start never changes it, an existing container refuses one, and a kept data volume (from `remove --keep-data`) keeps the password it was made with (a different choice is refused). Engines without a password (Redis, Chroma, Qdrant, Weaviate) and Couchbase (set in its web console) refuse the options. The user name is fixed per engine (`postgres`, `root`, `admin`, `elastic`). Generated passwords (24 random bytes as hex) go in `~/.local/share/bxrig/databases/<container>/` (`password` and `database.env`, mode 600, plus `meta.json` with the port) and reach the container through `--env-file`, never on a command line. Nothing changes system settings: when `vm.max_map_count` is too low `start` stops with the `sudo sysctl -w` line to run. Images are pinned and were checked on Docker Hub on 2026-11-10 (Elasticsearch's from Elastic's docs).

### 13.11 `dotfiles`: your own dotfiles repository (decided with the owner 2026-11-11)

```
bxrig dotfiles plan REPO [--method=chezmoi|yadm|stow|links] [--json]    clones the repo into BxRig's data folder; changes nothing in your home
bxrig dotfiles apply REPO [--method=M] [--overwrite] [--yes] [--dry-run] [--json]
bxrig dotfiles status | undo [--yes] [--dry-run] [--json]
```

`REPO` is a git URL or a local path. **The method is detected** (`--method` overrides): `chezmoi` (`.chezmoiroot`, `.chezmoiignore`, or `dot_` / `.chezmoi*` names), then `yadm` (`.config/yadm/`, or `##` alternate names), then `stow` (`.stowrc`, `.stow-local-ignore`, or only top-level package folders that hold dotfiles), else `links`.

**Your dotfiles win, but nothing is replaced unasked.** The plan splits the repo's files into new, already in place (a link to the repo, or an identical file) and **conflicts** (files you already have that would be replaced; chezmoi templates always count). `apply --yes` needs your approval of the conflicts: `--overwrite`, or a `y` at the prompt (read from `/dev/tty`, so a headless run without `--overwrite` exits 2 and changes nothing). Every replaced file is first moved into `~/.local/state/bxrig/backups/dotfiles/<time>/`; if a step then fails (exit 6) the originals are put back. `status` shows what was applied; `undo --yes` removes the links BxRig made (`stow -D` for stow) and restores the originals (for chezmoi and yadm only the originals come back: the files those tools created stay, remove them with the tool).

| Method | Files go to your home by | Applied with |
|---|---|---|
| `links` | one symlink per file (folders are never replaced by a link) | `ln -s` |
| `stow` | each top-level folder is a package | `stow -d CLONE -t HOME -R PACKAGES` |
| `chezmoi` | `dot_`, `private_`, `executable_`, ... prefixes and `.tmpl` are mapped to the plain path for the conflict list | `chezmoi apply --source CLONE --force` |
| `yadm` | `##` alternate suffixes are mapped to the plain name | `yadm clone -f --no-bootstrap REPO` (`yadm pull` when it is already set up) |

Repo-only files (`.git`, `README*`, `LICENSE*`, `.gitignore`, `.stow-local-ignore`...) are never linked. A missing tool (`chezmoi`, `yadm`, `stow`; Arch `extra`) is installed with `sudo pacman -S --needed` as the first step of `apply` (the plan says so). One repository can be set up at a time: a second one is refused (exit 4) until `undo`. Exits: 0 done, 2 no `--yes` or conflicts not approved, 4 precondition (cannot clone, unknown method, nothing to apply, tool not installable), 6 a step failed. The wizard's Import page asks for the repository (empty skips); `init` runs `dotfiles apply REPO` **last**, so your files win over the starter configs, and the conflict question appears at the terminal.

Tested against real git repositories and fake tools (`stow`, `chezmoi`, `yadm`, `pacman`); the real tools have not been run. Private repositories and credentials are git's business (SSH keys or a credential helper must already work).

### 13.13 Secrets: one way to store and load API keys (decided with the owner 2026-11-11)

`bxrig secrets` is the single way to keep API keys and tokens. Every machine uses the same commands; `export`/`import` (later) moves them between machines.

| Command | Does |
| --- | --- |
| `secrets status` | backend in use, whether a keyring is available, how many secrets are stored |
| `secrets set NAME [--from-file=F]` | stores a value: typed hidden at the terminal, or read from a file. Never a command-line value. Replaces an existing one |
| `secrets list` | names only, with the coding agent that reads each known key |
| `secrets get NAME [--show]` | says whether it is set and its length; `--show` prints the value |
| `secrets unset NAME --yes` | deletes a value (plan without `--yes`, exit 2) |
| `secrets run [NAMES...] [--strict] -- CMD...` | runs CMD with those secrets in its own environment only; exit code is CMD's. A name that is not set is skipped, `--strict` exits 4 |
| `secrets env [NAMES...]` | prints `export NAME='value'` lines for `eval` (all stored names when none given) |

- Names are environment variable names: capital letters, digits, underscores (`ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `GEMINI_API_KEY`).
- Backend: the desktop keyring through `secret-tool` (libsecret) when `secret-tool` exists and `org.freedesktop.secrets` is on the user D-Bus (running or activatable); otherwise private files (`~/.local/share/bxrig/secrets/NAME`, mode 600 in a mode 700 folder). The choice is saved in `~/.config/bxrig/secrets.json` and shown by `status`. Keyring entries carry the attributes `service=bxrig name=NAME`.
- Values are passed to `secret-tool` and to programs through standard input and the process environment, never through a command line, a temp file, a log, or `answers.json`.
- `set` is interactive on purpose and needs no `--yes`.
- Exit codes: 0 done, 2 usage or plan without `--yes`, 4 precondition (bad name, secret not set, no value), 6 the store failed.
Loading into shells (default is per command, global is opt-in per key):
- `secrets apply [--yes]` writes `~/.config/bxrig/secrets.sh` (bash, zsh) and `secrets.fish`. They hold no values: one wrapper per agent command whose key is stored (`claude() { bxrig secrets run ANTHROPIC_API_KEY -- command claude "$@"; }`). `secrets set` runs it automatically. The shell init templates source these files.
- `secrets global on NAME --yes | off NAME | show`: exports a key to every new shell. `on` prints a warning first (every program, including AI agents and what they run, can read it). The values go to a session cache, `$XDG_RUNTIME_DIR/bxrig-secrets.env` and `.fish` (mode 600, tmpfs, wiped at logout), never to a config file. The loader files call `secrets unlock` once per login when the cache is missing (the keyring's single unlock prompt); `secrets lock` removes the cache. A globally exported key gets no wrapper.
Moving machines and the keyring:
- `secrets export FILE [--plain] [--force] --yes`: all stored secrets as `export NAME='value'` lines, encrypted with a passphrase by `age -p` (age asks on the terminal; the file is mode 600). `--plain` writes a readable .env instead (mode 600; the plan says so). An existing file is kept unless `--force`.
- `secrets import FILE [--overwrite] --yes`: reads an age file or a .env file; the plan lists each name as new, same or differs. A name that already has a different value is kept unless `--overwrite`. New machine: `install.sh`, `init --answers answers.json`, `secrets import`, `dotfiles apply`.
- `secrets setup [--keyring=kwallet|gnome-keyring|none] [--yes] [--dry-run]`: checks for a Secret Service on the user D-Bus (running or activatable). Installs `libsecret` (`secret-tool`, repo core) and `age` (repo extra) when missing; when no keyring exists, also `kwallet` on Plasma or `gnome-keyring` elsewhere, or the one named. `--keyring=none` installs no keyring and saves the file backend. The plan names what it installs. Package names and `secret-tool` in libsecret were checked on archlinux.org on 2026-11-11.
Secret types and providers (decided with the owner 2026-11-11):

It shows the BxRig wordmark in the cyan to green gradient, the tagline and "Powered by BoxLang", checks the machine (CachyOS or Arch, not root, x86_64, sudo), downloads the channel's `bxrig-linux-x86_64` and `bootstrap.tar.gz`, verifies the Ed25519 signature of the release information (`version-latest.properties.sig`, OpenSSL, public key embedded in the published script) and the SHA-256 of both files against it, runs the stages of `bootstrap/install.sh` (`packages`, `toolchains`, `binary --binary`, `core`) behind spinners, then the setup wizard. There is no custom menu: it installs everything the wizard's defaults call for. Log: `~/.cache/bxrig/install.log`.
- **No human input:** `... | bash -s -- --yes [--answers FILE] [--channel stable|beta] [--no-wizard]`. `--yes` never asks (it needs passwordless sudo or a primed `sudo -v`), the wizard then runs `bxrig init --answers FILE --yes` or, without a file, `bxrig init --defaults --yes` (the wizard's default answers). `--dry-run` shows the banner and checks and does nothing. `--base-url` or `BXRIG_BASE_URL` points elsewhere. Exit 1 on any failure (nothing is installed after a failed checksum), 2 when you decline. `--source SPEC` (`BXRIG_SOURCE`, decided 2026-11-18): `stable` (default), `beta` (= `--channel beta`) or `github:OWNER/REPO@REF` (REF a branch, tag or commit; `github:@REF` and `github:REF` mean `ortus-boxlang/BxRig`; OWNER and REPO `[A-Za-z0-9._-]+`, REF `[A-Za-z0-9._/@+-]+` with no leading dash, no `..`, no leading or trailing slash; bad values and a `--channel` that disagrees exit 1). The github source skips the signed release: it is UNSIGNED (warning; `--yes` or the typed word `unsigned` at a terminal, else exit 2 before any download), downloads `codeload.github.com/OWNER/REPO/tar.gz/REF` (`GITHUB_TOKEN` or `GH_TOKEN` as a header through a curl config on stdin, never printed or logged; refuses paths outside the top folder), runs the tree's own `bootstrap/install.sh` stages (`binary --yes --force` builds from the tree's `src/Main.bx`), then the wizard from that binary. `--dry-run` with a github source downloads and unpacks it, prints the resolved commit and the tree's `install.sh --dry-run` plan, installs nothing. The source and the commit (the pax header `git archive` writes into the tarball) go to `~/.cache/bxrig/install.log` and `~/.local/share/bxrig/install-source`; `bxrig update` does not read that file (the binary differs from the channel's, so `update check` says an update exists and `update apply --yes` would replace the build). A github source compiles bxrig, so unless the user chose a MatchBox it passes `--matchbox-from-source` (the manifest branch, `bxrig`) to the toolchains stage; `--snapshot` is passed as given and the binary stage then stops at the capability check (never a silent switch). MatchBox options (decided 2026-11-18, see 14.1): `--snapshot` (`BXRIG_MATCHBOX_CHANNEL=snapshot`), `--matchbox-branch REF` (`BXRIG_MATCHBOX_BRANCH`), `--matchbox-repo OWNER/NAME` (`BXRIG_MATCHBOX_REPO`, `^[A-Za-z0-9._-]+/[A-Za-z0-9._-]+$`, needs a branch) and `--matchbox-from-source` (= `--matchbox-branch bxrig`) are validated (bad values and `--snapshot` with a branch exit 1) and passed through to the toolchains stage; the stable path with the prebuilt binary needs no capable MatchBox, so its stages are unchanged.
- **Channels and S3 (`downloads.ortussolutions.com/ortussolutions/bxrig/`):** `stable/` (a `v*` tag), `beta/` (every push to `development`, the bleeding edge), each with `bxrig-linux-x86_64`, `.sha256`, `bootstrap.tar.gz`, `.sha256` and `version-latest.properties` (`version`, `commit`, `sha256`, `channel`, `builtAt`); `snapshots/<version>-<sha>/` keeps every beta build and `releases/<version>/` every stable one (uploads never delete). CI job 6 publishes when the AWS secrets exist (`AWS_ACCESS_KEY`, `AWS_ACCESS_SECRET`).
- **`update check [--notify]`:** compares the running binary's SHA-256 with the channel's `version-latest.properties`; exit 10 when an update is available, 0 when current, 5 when the server is unreachable; also counts pending system updates (`checkupdates`). `update apply [--yes]` downloads the channel's binary, verifies its SHA-256 against its `.sha256` and the signed release information, and replaces the installed binary atomically (exit 5 on a mismatch or a bad signature, the old binary stays). `update channel [stable|beta]` shows or sets the channel (`~/.config/bxrig/update.json`; the wizard asks `update_channel`, default stable). `update notifications on|off|status` manages a daily user timer `bxrig-update-check.timer` that runs `update check --notify` and shows a notification (`noctalia msg notification-show`, else `notify-send`); the wizard asks `update_notifications`, default on. `system update [--yes]` takes a snapshot first when snapper or timeshift is present, then `sudo pacman -Syu --noconfirm` and, with yay, `yay -Sua --noconfirm`. The menu has Settings entries for check, apply, both channels, notifications on and off, and system update.
- **Signing (owner decision 2026-11-13: sign the installer and update):** CI signs every `version-latest.properties` and `install.sh` with Ed25519 (`openssl pkeyutl -sign -rawin`) using the secret `BXRIG_SIGNING_KEY`; the properties carry `sha256` (binary) and `bootstrap_sha256` (bundle). The public key is `keys/release.pub` (made with `scripts/gen-signing-key.sh`), embedded into the binary (`bootstrap/gen-releasekey.sh` writes `src/bxrig/ReleaseKey.bx`) and into the published `install.sh` (CI replaces `@@PUBKEY_B64@@`). With a key a missing or invalid signature, or a file that does not match the signed hash, stops the install or update before anything changes (exit 1 for the installer, 5 for `update`); without a key (a development build) only SHA-256 is checked. Limit: the very first `curl | bash` still trusts the script it downloads (TLS and the bucket), so the signature protects the files the script fetches and every later update; verify `install.sh.sig` by hand with `keys/release.pub` for a stricter first install.
- **`system updates [--json]` (read only, for the System bar panel):** `{ total, repo_count, aur_count, packages: [ { name, old, new, repo } ], needs_reboot, reboot_pending, reboot_stale, reboot_reasons, last_update, last_update_epoch, last_update_ago, aur_helper, aur_error, snapshot_tool }`. Repository rows come from `checkupdates` (exit 0 rows, 2 none, 1 error), AUR rows from `yay -Qua` or `paru -Qua` (no helper: none, not an error); `repo` of a package is `repo` or `aur`. Restart rule: `reboot_pending` when a waiting update replaces a kernel (linux and its lts, zen, hardened, rt, cachyos flavours, not headers, docs or driver modules), systemd, glibc, linux-firmware, a microcode package or the NVIDIA driver; `reboot_stale` when `/usr/lib/modules/$(uname -r)` is gone; `needs_reboot` is either. Exit 0 always except 4 (no pacman, no `checkupdates`, or `checkupdates` failed). Class `SystemUpdates`; the parsers are `Pacman.parseUpgrades`, `Pacman.pendingUpdates` and `Aur.pendingUpdates` (`Aur.updateHelper` is yay, else paru; installs still use yay).
- **`system update [--repo|--aur|--all] [--yes] [--dry-run]`:** a snapshot first (snapper, else timeshift, else a note that there is none), then `sudo pacman -Syu --noconfirm` (`--repo`), the AUR helper `-Sua --noconfirm` (`--aur`, yay else paru; exit 4 without one) or both (`--all`, the default). Without `--yes` the plan is printed (exit 2), `--dry-run` shows it and exits 0; two scopes together are a usage error (2). Text mode prints `[n/N] command` as each step starts; the data of a run carries `needs_reboot` (the kernel that runs was replaced).
- Tests: `tests/web-install-test.sh` (fake server and stages, signed and unsigned), `tests/update-test.sh`, `tests/system-updates-test.sh`, `system_updates_test.bxs`, `init_plan_test.bxs`.

### 13.32 Themes, the Neovim layer and the Starship BoxLang module (decided with the owner 2026-11-13)

- **Command:** `theme list|show NAME|set NAME [--mode=theme|dark|light|auto] [--keep-wallpaper]|random|next|mode theme|dark|light|auto|install GIT_URL [--name=N] [--force]|import PATH [--name=N] [--force]|remove NAME|status`, all with `--dry-run` where they change anything and `--json`. Like `runner set` these are settings: they act at once (no `--yes`). Exit: 0 done, 2 bad usage or mode, 4 unknown or invalid theme (nothing is written), 6 a file could not be written.
- **Theme format:** a folder in the `colors.toml` theme format, so themes move both ways: `colors.toml`, optional `neovim.lua`, optional `backgrounds/` (the first file is the wallpaper). Both `colors.toml` shapes are read: the named one (`accent background foreground selection muted red green yellow blue magenta cyan bright_*`, `mode = "dark"|"light"`) and the older `color0..color15` one. The named shape maps to the 16 ANSI slots: black is `background`, white is `foreground`, bright black is `muted`, bright white is `bright_foreground`. A missing required key or a value that is not `#rrggbb` rejects the whole theme. Light or dark is the file's `mode`, else the background luminance (above 0.4 is light).
- **Sources, first match wins:** `~/.config/bxrig/themes/NAME` (installed or imported), theme folders of other desktops found on disk (`~/.config/omarchy/themes/NAME` and `~/.local/share/omarchy/themes/NAME`), then 15 bundled in the binary: 10 community themes (catppuccin, catppuccin-latte, tokyo-night, gruvbox, nord, rose-pine, kanagawa, everforest, matte-black, flexoki-light; MIT, credited in `themes/NOTICE.md`) and 5 of ours (`bxrig`, `bxrig-light`, `bxrig-midnight`, `bxrig-cyan`, `bxrig-forest`). `install` takes an https git URL only (a repository named `omarchy-NAME-theme` becomes `NAME`), clones it shallow, validates it, refuses symlinks and an existing theme (without `--force`), and copies it without `.git`. Only your own themes can be removed, never the current one.
- **What `set` writes** (through the config service: atomic, backed up, journalled; unchanged files are skipped): the Noctalia palette `~/.config/noctalia/palettes/BxRigTheme.json` (the 16 roles are derived from the theme, both variants carry the same colours), `~/.config/bxrig/theme/{ghostty,kitty.conf,alacritty.toml,foot.ini,hypr.lua}`, `~/.config/btop/themes/bxrig.theme`, `~/.local/state/bxrig/current/theme/neovim.lua` and every theme's `neovim.lua` in `~/.config/bxrig/nvim-themes/`. Then it tells the desktop: `noctalia msg color-scheme-set custom BxRigTheme`, `theme-mode-set`, `wallpaper-set` (a bundled BxRig theme brings one of our wallpapers, an on-disk theme its `backgrounds/`, other bundled themes keep yours), `plasma-apply-colorscheme BreezeDark|BreezeLight` on KDE, `hyprctl reload` inside Hyprland. A missing or silent Noctalia is a note, not an error. Mode `theme` (default) follows the theme; `dark`, `light` or `auto` pin it; the mode survives `set`.
- **Where the files are used:** the terminal starters (written once) include `~/.config/bxrig/theme/...` (ghostty `config-file = ?path`, kitty `include`, alacritty `[general] import`, foot `include=`) and `TerminalConfig.apply` writes the default theme files, so an include never points at nothing; your own terminal configs are never edited. The managed `hypr/bxrig.lua` reads `theme/hypr.lua` (border colours). btop needs `color_theme = "bxrig"` in your `btop.conf`, which we do not edit.
- **Not themed in v1:** the Starship prompt (fixed Catppuccin Mocha palette, no include mechanism), VS Code, Chromium, GTK and Qt apps (whether `noctalia msg templates-apply` themes them is unverified).
- **Neovim layer** (`editor lazyvim|boxlang|status|refresh`): after the starter is cloned (an existing `~/.config/nvim` is never touched) the layer is added: `lua/config/bxrig.lua` (relativenumber off, autoformat off, OSC 52 clipboard over SSH, loaded by one line added to `options.lua`), `lua/plugins/bxrig.lua` (no news popups, no scroll animation, transparent lualine), `plugin/after/bxrig-transparency.lua`, `lua/plugins/boxlang.lua` (`ortus-boxlang/vim-boxlang`, loaded at startup so its ftdetect runs first), `lua/plugins/bxrig-themes.lua` (every theme's colourscheme plugin listed lazily from `nvim-themes/`), `lua/plugins/bxrig-theme-reload.lua` (a libuv watcher re-applies the colourscheme when the theme file changes), `lua/plugins/theme.lua` (a link to the current theme's `neovim.lua`) and the neo-tree extra merged into `lazyvim.json`. Written by us. `editor boxlang` adds only the plugin file to a LazyVim config you have. `refresh` rewrites the files still as BxRig wrote them and keeps the ones you changed unless `--force`.
- **Theme depth (2026-11-13):** `set` also writes `theme/tmux.conf`, `theme/fzf.sh` (FZF_DEFAULT_OPTS), `theme/rofi/theme.rasi` (plus a `rofi/config.rasi` stub only when none exists), GTK 4 and 3 `gtk.css` (libadwaita `@define-color` names, adw-gtk3 for GTK 3), qt6ct and qt5ct `colors/bxrig.conf` (21 ARGB roles), `fuzzel/fuzzel.ini` and `wofi/style.css`: 18 files in all, each kept when you edit it. It sets gsettings `color-scheme` (prefer-dark or prefer-light) and the adw-gtk3 theme when installed. `theme vscode [--yes] [--dry-run]` is opt-in: plan first (exit 2), then a plain-JSON merge into `workbench.colorCustomizations` of Code, Code - OSS, VSCodium or Cursor with a backup; a settings.json with comments or trailing commas is skipped. Exit 4 when no settings file exists. Unverified on a real desktop: that GTK, Qt, rofi, fuzzel and wofi pick the files up as written.
- **Wizard:** `theme_name` (default `bxrig`; a Light answer with the default picks `bxrig-light`) is chosen on its own Theme page (not on the Look page) and runs `theme set` after the terminals, optional, for Hyprland and Plasma; when a theme is applied already, choosing `bxrig` again still runs `theme set bxrig` (`InitPlan.plan` is told the applied theme); the editor answer now includes the layer and BoxLang syntax. The Themes menu has next, random, the five BxRig themes, the four modes and status.
- **Starship:** the starter prompt shows the BoxLang version like Java: `custom.boxlang` (`${custom.boxlang}` in the format), shown only in a directory with `.bx .bxs .bxm .cfc .cfm .cfs` files or `box.json`, `Application.bx`, `Application.cfc`. It has no `when` (Starship shows a custom module when ANY of `when`, `detect_files`, `detect_extensions` matches, so `when` would show it everywhere); its command prints the `~/.bvm/current` symlink name (honouring `BVM_HOME`) or nothing. The starter is written once, so existing installs see the change with `bxrig config diff starship`.
- **Verified and not:** tested with fake `noctalia`, `plasma-apply-colorscheme`, `hyprctl`, `git`, `pacman` (`tests/theme-test.sh`, `tests/editor-test.sh`, `tests/theme_colors_test.bxs`, `tests/init_plan_test.bxs`); the Lua files only parse-checked and the theme loader run against a stub `vim` (no Neovim here); the Starship command logic run in `sh`, not by Starship. **Unverified on a real machine:** the Noctalia IPC argument forms against a running Noctalia, Hyprland's `dofile` and `hl.config` from the managed module and `hyprctl reload` with a Lua config, ghostty's `?` optional include, kitty, alacritty `[general] import` and foot `include=` with a missing file, the foot `[colors-dark]` section on the installed foot, lazy.nvim picking the colourscheme plugin up on `:colorscheme`, `vim-boxlang` loading with `lazy = false`, Starship hiding a custom module on empty output.

### 13.33 Virtual machines: Windows and Linux desktops in containers (decided with the owner 2026-11-13)

- **Command:** `vm list|status [NAME]|size [NAME]|info NAME [--show-password]|doctor|versions linux|windows|create windows [NAME] [--version=V] [--ram=] [--cpus=] [--disk=] [--share=PATH|none]|create linux NAME [--tag=T] [--cpus=] [--memory=] [--share=PATH|none] [--gpu=none|auto|intel|amd|nvidia]|start|stop|logs NAME|open NAME [--web] [--fullscreen]|remove NAME [--keep-data]`, with `--json`. `create` and `remove` are plans until `--yes` (`--dry-run` too). Exit: 0 done, 2 plan or bad usage, 4 precondition (bad name or version, KVM unusable, no engine, no terminal to choose a Windows version on, GPU not possible), 6 a command failed.
- **Two kinds, any number of each.** Every VM has a name (`[a-z0-9-]`, up to 31) and a record in `~/.config/bxrig/vms/NAME.json` (mode 600). Windows is `dockurr/windows`; a Linux desktop is LinuxServer's `lscr.io/linuxserver/webtop:TAG`. The container is `bxrig-vm-NAME`, labelled `io.bxrig.vm`. The first Windows is named `windows`. The engine is the one `bxrig db engine` chose (Podman by default).
- **Where things live (documented for the user in `docs/guides/vms.md`):** data in `~/.local/share/bxrig/vms/NAME` (`storage` is the Windows disk, `config` is the Linux desktop's home folder), the record above, the password in the keyring as `BXRIG_VM_<NAME>_PASSWORD` (`bxrig secrets`), an app-menu launcher `~/.local/share/applications/bxrig-vm-NAME.desktop` (runs `vm open NAME`), and a shared folder: `~/Windows` (drive Z:) or `~/Shared` (`/config/Shared`), or `--share=none`. `remove` deletes the container, the data, the password, the record and the launcher; the shared folder is never deleted; `--keep-data` keeps data, password and record. `size` is `du` of the data folder; the images are in the engine (`podman image ls`).
- **Security:** ports bind to `127.0.0.1` only (the webtop terminal has passwordless sudo; the Windows web viewer and RDP are for you). The password is generated (16 random bytes), stored in the keyring, and reaches the container through an env file (mode 600) that is deleted right after `run`. The default `admin` password of dockur is never used.
- **Ports:** Linux 3001 upward (HTTPS, a self-signed certificate: accept it once); Windows web viewer 8006 upward and RDP 3389 upward (TCP and UDP); each VM takes the first port no record uses and nothing listens on.
- **Windows:** `--version` takes any dockur VERSION value (25, `vm versions windows`). Without it at a terminal, a picker shows ten choices with sizes and notes (11 Pro, 11 LTSC, 11 Enterprise, 10 Pro, 10 LTSC, Tiny11, Tiny11 Core, Tiny10, Server 2025 and 2022; the Tiny builds are marked UNOFFICIAL); with no terminal it exits 4 (a script passes `--version`; with `--json` the picker text goes to the terminal device, never stdout). Defaults: RAM half the machine (4G to 8G), CPUs half (2 to 8), disk 64G. Run: `--device /dev/kvm --device /dev/net/tun --cap-add NET_ADMIN --stop-timeout 120`, env `VERSION RAM_SIZE CPU_CORES DISK_SIZE USERNAME PASSWORD`. The install downloads the ISO inside the container on the first start (3 to 8 GB) and takes a while; you need your own Windows license (dockur uses generic trial keys that do not activate). `open` starts the VM if needed, waits for RDP, then runs the first FreeRDP client found (`sdl-freerdp3`, `sdl-freerdp`, `xfreerdp3`, `xfreerdp`, `wlfreerdp3`, `wlfreerdp`) with `/args-from:file:PATH`: a mode 600 file holding `/v:` `/u:` `/p:` `/cert:ignore` `+clipboard` `/dynamic-resolution` `/title:` (and `/f`), so the password is never on a command line; the file is removed after 15 seconds. While Windows is still installing, `open` says so and points at `open --web` (the browser viewer).
- **Linux:** 21 tags from the webtop page (Ubuntu, Debian, Fedora, Arch: xfce, kde, mate, i3, and lxqt for Ubuntu; Alpine with the upstream `latest` tag as `alpine-xfce`); default `ubuntu-xfce`. The `dev` tag and the deprecated Enterprise Linux tags are not offered; KDE tags are Wayland only. Run: `--shm-size 1gb`, env `PUID PGID TZ CUSTOM_USER=bxrig PASSWORD`, `-v data:/config`. Rootless Podman maps the container's root to you, so PUID and PGID are 0 there (files stay yours); Docker uses your ids. `--cpus` and `--memory` map to the engine flags. When the host has no IPv6 (`/proc/sys/net/ipv6` missing) the container also gets `DISABLE_IPV6=true`, because the image's nginx otherwise fails on `listen [::]` (found by running the real image; `doctor` notes it).
- **GPU (Linux desktops, opt-in):** `intel` and `amd` add `--device /dev/dri` (needs it to exist); `auto` does that when `/dev/dri` exists and nothing otherwise; `nvidia` follows the webtop docs: Docker gets `--runtime nvidia --gpus all --device /dev/nvidia-modeset`, Podman gets CDI (`--device nvidia.com/gpu=all --device /dev/nvidia-modeset`). The Alpine tags refuse NVIDIA. `doctor` reports `/dev/dri`, the NVIDIA driver version (the docs ask for 580 or newer) and `nvidia-ctk`. Windows has no GPU option.
- **Wizard and menu:** two optional questions after the databases: `vm_windows` (none or one of the ten, with descriptions) and `vm_linux` (none or six tags); they become optional steps `vm create windows --version=V` and `vm create linux desktop --tag=T`, and add the Podman install when no engine answer was given. The menu has a Virtual machines entry (list, sizes, doctor, the two version tables).
- **Verified and not:** tested against fake Podman and Docker (every run argument, files, modes, ports, passwords, launchers, exit codes) in `tests/vm-test.sh` and `tests/init_plan_test.bxs`. **Also run for real (2026-11-13, a sandbox with Docker 29.9.2, no KVM, no IPv6, running as root):** `vm create linux` with the real `lscr.io/linuxserver/webtop:ubuntu-xfce` image through `bxrig`: the published `127.0.0.1:3001` answers 401 without credentials, 200 with the generated password and 401 with a wrong one; the shared folder works both ways; `start`, `stop`, `status`, `size`, `info`, `open` (browser launch only) and `remove` behave. **Never run:** Windows (no `/dev/kvm` here), Podman, a non-root user (so PUID and file ownership are untested), GPUs, FreeRDP. **Unverified on a real machine:** Windows booting under rootless Podman (`/dev/kvm`, `/dev/net/tun`, `NET_ADMIN`), RDP through the published `127.0.0.1` port (dockur documents the container's own IP too), dockur on a Btrfs disk (CachyOS default; not checked in its README), webtop under rootless Podman with PUID 0 and as a non-root Docker user, the NVIDIA paths (driver 580 or newer from a `.run` file per the docs, whether CachyOS's packaged driver counts, CDI on Podman, the Arch package name `nvidia-container-toolkit`), and the FreeRDP argument file (`/args-from:file:` read from the FreeRDP 3 source, the client binary names are a best guess).

### 13.37 Power (decided with the owner 2026-11-13)

- **`bxrig power status|profile|lid|hibernate|charge-limit|setup|doctor`.** `profile [performance|balanced|saver]` uses `powerprofilesctl get|set` (`saver` is `power-saver`).
- **`status --json`** (2026-11-17, the Power panel reads it): `data.battery[]` has one entry per `BAT*` with `name`, `percent`, `status`, `state` (`charging|discharging|full|not_charging|unknown`), `watts` (power draw), `time_remaining_minutes` (to empty when discharging, to full when charging), `health_percent` (full over design capacity), `cycles`, `charge_limit` and `charge_limit_supported`. A number the battery does not report is `-1`. The rest of `data`: `on_ac` (a Mains or USB-C supply is online), `profile`, `lid` (`default|suspend|hibernate|lock|ignore|mixed|custom`), `lid_battery`, `lid_ac`, `charge_limit_supported`, `power_profiles_daemon`, `upower`. Values come from sysfs (`energy_now`/`power_now` or `charge_now`/`current_now`, `*_full`, `*_full_design`, `cycle_count`).
- **`lid [battery|ac] suspend|hibernate|lock|ignore`** writes the logind drop-in `/etc/systemd/logind.conf.d/50-bxrig-lid.conf` with `sudo install -Dm644`: `HandleLidSwitch` is the action on battery, `HandleLidSwitchExternalPower` the action on AC power, `HandleLidSwitchDocked=ignore`. Without `battery` or `ac` both get the action. The side that is not named keeps its value, or `suspend` (the systemd default) when there is no drop-in, and both lines are always written so the AC line never follows the battery one by accident. It is a plan (exit 2) without `--yes`, and logind reads it from the next login or reboot (logind is not restarted: that would end the session). A plan for `hibernate` warns when hibernation is not ready.
- **`hibernate [--yes]`** runs the readiness checks first and exits 4 with the reasons when one fails: disk swap at least the size of RAM (`/proc/swaps`, zram does not count), `resume=` (and `resume_offset=` for a swap file) on the kernel command line, and the kernel offering the `disk` state (`/sys/power/state`) without secure boot lockdown (`/sys/kernel/security/lockdown`). Ready: a plan (exit 2) until `--yes`, then `systemctl hibernate --no-block` (without `--no-block` the call would wait until the machine wakes up). The initramfs `resume` hook cannot be read reliably and is not checked. `doctor` shows the same checks as `hibernation` (swap), `resume` and `hibernate-kernel`.
- **`charge-limit [PERCENT|off|status] [--yes]`** uses the kernel attribute `charge_control_end_threshold` of each `BAT*` (Linux ABI `sysfs-class-power`: "a battery percentage level, above which charging will stop"; 0 to 100, drivers round to what the hardware supports). PERCENT is 40 to 100. It writes `/etc/systemd/system/bxrig-charge-limit.service` (a oneshot that writes the value at boot and after suspend, hibernate and hybrid sleep, because some firmware resets it) with `sudo install`, then `daemon-reload`, `enable --now` and `restart`. `off` (or 100) disables and removes the unit and writes 100 to the attribute. `status` is information (exit 0, `supported`, `limit`, `persisted`). On a laptop whose battery has no such attribute `PERCENT` and `off` exit 4. A plan (exit 2) without `--yes`. **Not verified on real hardware** (the fake sysfs of `power-test.sh` only).
- **`setup`** installs and enables `power-profiles-daemon` and `upower` (`sudo pacman -S --needed --noconfirm`, `sudo systemctl enable --now`). **On a machine without a battery it does nothing** (exit 0, `skipped: "no battery"`) unless `--force`. The init plan has an optional `power-setup` step behind the answer `power_setup`; no wizard question exists yet.
- **`doctor`** checks battery, the two daemons, the lid action, zram, and (laptops only) the hibernation checks and whether the battery has a charge limit. Problems are reported, never fixed silently.
- **Not built:** configuring hibernation (resume offset, initramfs hook) and TLP; battery display and brightness stay with Noctalia and powerdevil. CachyOS ships no laptop power tooling (`cachyos-settings` pulls zram, ananicy, inxi, iw, wireless-regdb), so this is ours.
- **Menu:** Setup > Power. **Verified:** `tests/power-test.sh` (fake sysfs, `/proc/swaps`, command line, `/sys/power`, lockdown, meminfo, powerprofilesctl, systemctl, sudo, pacman). Not verified on a real laptop.

### 13.41 NAS as a first-class namespace (decided with the owner 2026-11-13)

- **`bxrig nas`** keeps every NAS you use in `~/.config/bxrig/nas.json` (name, host, protocol `smb` or `nfs`, user, optional SMB version, and the shares you mounted). `discover` browses the network with `avahi-browse -rtp _smb._tcp` and `_nfs._tcp` (IPv4 only). `setup` installs `cifs-utils nfs-utils smbclient avahi nss-mdns rsync` and enables `avahi-daemon` (a plan without `--yes`; every tool was checked in the Arch repos and its binary exists after install).
- **`add NAME --host=H`** needs `--user` and a password for SMB (`--ask-password`, typed hidden, or `--password-file=F`); the password goes to the keyring as `BXRIG_NAS_<NAME>_PASSWORD` and never into `nas.json`. NFS needs neither. Names are `^[a-z][a-z0-9-]{0,30}$`.
- **`shares NAME`** lists SMB shares with `smbclient -g -L HOST -A AUTHFILE` (the auth file is a private temp file, deleted after; no password on a command line; `IPC$` and other hidden shares are dropped) or NFS exports with `showmount -e --no-headers`.
- **`mount|unmount NAME SHARE`** mounts at `~/NAS/NAME/LEAF` (`BXRIG_NAS_HOME` overrides) with `sudo mount -t cifs|nfs`; the SMB options are `credentials=/etc/bxrig/nas/NAME.cred,uid,gid,iocharset=utf8,file_mode=0600,dir_mode=0700` plus `vers=` only when you set one (otherwise the kernel negotiates the highest version both sides support). **The credentials file is root-only (mode 600) because `mount.cifs` reads it as root**; the plan says so.
- **`auto on|off NAME SHARE`** writes `<escaped-path>.mount` and `.automount` units to `/etc/systemd/system` (`Options=...,nofail`, `TimeoutSec=20`, `TimeoutIdleSec=600`, wanted by `multi-user.target`), runs `daemon-reload` and `enable --now`, so a sleeping NAS never blocks login. `off` disables and removes them; a NAS with automatic mounts is not removed (exit 4) until they are off.
- **`test NAME [SHARE]`** checks: reachable (TCP 445 or 2049), signed in or exports readable, mounted (`findmnt`), writable (a probe file), free space. Exit 4 when a check fails.
- **`sync NAME SRC --to=SHARE[/PATH]`** is a plain `rsync -a` mirror to a mounted share. Nothing is deleted from the NAS unless you add `--delete`, and the plan says so in capitals.
- **`use NAME SHARE [--path=bxrig-backup]`** records `targets.nas-NAME` in `~/.config/bxrig/backup.json` (`{type: nas, nas, share, path}`); `backup data setup` reads it.
- **Verified:** `tests/nas-test.sh` with fake avahi-browse, smbclient, showmount, findmnt, rsync, sudo and a fake `/etc`. **Not verified on a real Synology:** DSM share permissions, SMB signing, NFS export options, `nss-mdns` name resolution.

### 13.42 `refresh` and `reinstall` (decided with the owner 2026-11-13)

- **No factory reset.** `bxrig refresh COMPONENT` puts managed config back to what BxRig ships and never installs a package. Components: `hyprland` (runs `keys apply`, `appearance apply`, `display apply`; with `--starter` also the starter `hyprland.lua`), `noctalia` (`theme set CURRENT`, `appearance apply`, `noctalia msg config-reload`; with `--starter` also the Noctalia starter files), `terminals` (the starter config of each installed terminal, then the theme includes), `shell` (`starship.toml`, the shell init and the line in `.zshrc` or `.bashrc`), `nvim` (`editor refresh`), `theme` (`theme set CURRENT`, `appearance apply`), `all`, and `list`.
- **Semantics are the config service's:** a clean file is left alone, a missing or outdated one is written, a file you edited (`drifted`) is kept and reported, and `--force` overwrites it after a backup (`config history`, `config restore`). A link or special file in the way blocks (exit 8 in the service, shown as blocked). Without `--yes` it prints the plan and exits 2; `--dry-run` exits 0.
- **`reinstall`** is `init --rerun`: the way to install packages again.
- **Verified:** `tests/refresh-test.sh` (temp home, fake `bxrig` that logs the commands, a fake terminal): plan and dry run write nothing, files are written, a second run rewrites nothing clean, edits are kept, `--force` overwrites and takes a backup, each component runs its commands.

### 13.43 Backups: the config layer (decided with the owner 2026-11-13)

- **Three layers, one command.** `bxrig backup config` (your BxRig setup), `backup snapshots` (the system, Btrfs with snapper) and `backup data` (your files, restic) are built in that order; `backup send` and `backup export` move any of them, and `timemachine` shows them all. This section is the config layer; the others are added below as they land.
- **A snapshot** is `~/.local/share/bxrig/backups/config/ID.tar.gz` (mode 600) plus `ID.json`. `ID` is `yyyyMMddTHHmmss` (with `-xxxx` when two land in the same second). Inside: `files/` (paths under your home), `packages.txt` (`pacman -Qqe`), `foreign.txt` (`pacman -Qqm`), `meta.json`, and `secrets.bxs` only with `--with-secrets` (the output of `bxrig secrets export`, encrypted with a passphrase you type).
- **What is tracked** (under your home): `.config/bxrig`, `hypr`, `noctalia`, `ghostty`, `kitty`, `foot`, `alacritty`, `starship.toml`, `nvim`, `btop`, `fish`, `git`, `mimeapps.list`, `xdg-terminals.list`, `.zshrc`, `.bashrc`, `.gitconfig`, `.ssh/config`. `backup config add|remove PATH` changes the list (stored in `backup.json`); SSH keys, `gnupg`, `..` and absolute paths are refused. `.git`, `node_modules` and `*.log` are skipped.
- **Restore** shows a plan (which files are created or replaced; exit 2 without `--yes`), takes a **safety snapshot of the present** first, then copies the files back (`--only=PATH` limits it). `--packages` installs the explicit packages that are missing and exist in the repositories with `sudo pacman -S --needed --noconfirm`; AUR and local ones are listed for `yay`, never installed from here. `diff ID` compares a snapshot with now (files same, changed, missing, and missing packages).
- **Automatic:** `auto` is on by default. Before `update apply`, `system update`, `init`, `reinstall` and `refresh` (with `--yes`, never `--dry-run`) a snapshot is taken quietly, with the reason `before <command>`; it never stops the command. The newest 30 are kept (`prune --keep=N`).
- **Verified:** `tests/backup-config-test.sh` (temp home, fake pacman, sudo and bxrig). Not verified: a restore on a different machine.

- **`backup snapshots`** (system snapshots). Btrfs root: snapper. `setup [--home]` installs `snapper snap-pac` (and `grub-btrfs` only when GRUB is in use), creates the `root` config (`snapper -c root create-config /`; `--home` adds `/home`), sets the timeline to 5 hourly, 7 daily, 2 weekly, 1 monthly, 0 yearly (`snapper set-config TIMELINE_*`), and enables `snapper-timeline.timer` and `snapper-cleanup.timer` (and `grub-btrfsd.service`). snap-pac takes a snapshot before and after every pacman transaction through its own hooks. Other filesystems: it installs Timeshift (rsync mode), which takes full copies and needs one visit to its window to pick a disk. `list` reads `snapper --jsonout -c CONFIG list` (snapshot 0, the live system, is left out); `create [--description=T]` is `snapper create --description T -p`; `delete ID`; `changes ID` is `snapper status ID..0`; `restore ID PATH` is `snapper undochange ID..0 PATH` (files changed since are replaced, files that did not exist then are removed, so the plan says so). **There is no automatic whole-system rollback**: rolling back a Btrfs root depends on your subvolume layout, so you boot the snapshot from the GRUB menu and follow the Arch wiki, or restore folders with `restore`. Everything that changes the system is a plan without `--yes`. **Not verified on real Btrfs:** the JSON shape of `snapper --jsonout list` (the parser accepts a bare array or an object holding one array), the timers, `undochange`. Tested with fakes in `tests/backup-snapshots-test.sh`.

- **`backup data`** (your files, restic). A **target** is a place a restic repository lives: `local` (a path), `nas` (made by `nas use`, at `~/NAS/NAME/SHARE/PATH`), `sftp` (`sftp:user@host:/path`; port as `sftp:-p N user@host:/path`), `rest` (`rest:URL`), `s3` (`s3:ENDPOINT/BUCKET/PATH`, AWS when no endpoint; works for DigitalOcean Spaces, Wasabi, MinIO), `b2` (`b2:BUCKET:PATH`), `azure` (`azure:CONTAINER:/PATH`), `gs` (`gs:BUCKET:/PATH`, with `GOOGLE_PROJECT_ID` and `GOOGLE_APPLICATION_CREDENTIALS` as the project and the service-account file) and `rclone` (`rclone:REMOTE:PATH`; FTP and any rclone service). The environment variable names (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION`, `B2_ACCOUNT_ID`, `B2_ACCOUNT_KEY`, `AZURE_ACCOUNT_NAME`, `AZURE_ACCOUNT_KEY`, `RESTIC_REST_USERNAME`, `RESTIC_REST_PASSWORD`) and the address forms were read from restic's own documentation; the flags used (`-r` via `RESTIC_REPOSITORY`, `backup --tag --exclude --exclude-caches --one-file-system`, `forget --keep-daily|weekly|monthly --prune`, `snapshots --json`, `ls --json`, `restore --target --include`, `check --read-data-subset`) from the installed restic 0.19.1.
  - **Keys go straight to the keyring** (`target add ... --ask-keys`, typed hidden, or `--keys-file` with `KEY=VALUE` lines) as `BXRIG_BACKUP_<TARGET>_<KEY>`; the **repository password is generated at `init`** (24 random bytes, hex) and kept as `BXRIG_BACKUP_<TARGET>_PASSWORD`, with a reminder that losing it loses the backups. restic is started with these in its **environment**, never on a command line, and no key is written to `backup.json`.
  - `run` backs up the include list (default `Projects code dev Documents .ssh`, only the ones that exist) skipping the exclude list (default `node_modules target .gradle __pycache__ .venv venv .cache .next *.tmp`) and cache folders, on one filesystem, tagged `bxrig`; `list`, `files`, `restore ID --to=DIR [--include=PATH]` (into a folder you name, never over your files by itself), `verify [--deep]` (`restic check`, `--read-data-subset 5%`), `forget` (retention 7 daily, 4 weekly, 6 monthly by default, `retention` changes it; deletes older backups for good, so it is a plan first), `schedule hourly|daily|off` (user units `bxrig-backup.service` and `.timer`: `ConditionACPower=true` so it skips on battery, `Persistent=true` to catch up, a random delay up to 15 minutes; a failed scheduled run sends a Noctalia or `notify-send` notification). An unmounted NAS share exits 4 with the `nas mount` command.
  - **Verified:** `tests/backup-data-test.sh` with a fake restic that records its arguments and the variables it was given. **Not verified against a real cloud account, NAS or restic repository** in this environment.

- **`backup send` and `backup export`** (moving backups). `send ID|all --to=TARGET [--from=TARGET]` is `restic copy` into a second repository (a NAS and a cloud bucket, for a 3-2-1 setup): the destination is `RESTIC_REPOSITORY`, the source goes in `RESTIC_FROM_REPOSITORY` with `RESTIC_FROM_PASSWORD_COMMAND=printenv BXRIG_FROM_PW`, so no password is on a command line. restic reads one set of `AWS_*`, `B2_*` ... variables, so two repositories that need different values for the same variable (two S3 accounts) are refused (exit 4) with a pointer to `rclone sync`. `export data ID --to=FILE` is `restic dump --archive tar|zip --target FILE ID PATH` (zip when the name ends in `.zip`; `--path` limits it to a folder; an existing file is never overwritten), `export config ID --to=FILE.tar.gz` copies a config snapshot out as one file. **Config snapshots travel with the data backups**: `~/.local/share/bxrig/backups/config` is in the default include list, so a NAS or cloud target protects them with no extra step. System snapshots are not exportable. Tested in `tests/backup-move-test.sh` with a fake restic.

### 13.44 BxTimeMachine, the backup screen (decided with the owner 2026-11-13)

- **`bxrig timemachine [--demo] [--local]`** (also `bxrig bxtimemachine`) is **BxTimeMachine**, a full-screen terminal UI on MatchBox's canvas (the same one as the wizard) over **`bxrig backup timeline [--json] [--local]`**, which lists every backup in one structure: rows `system` (snapper), `config` (config snapshots), `files-NAME` (one per data target, from `restic snapshots --json`) and `mirror-NAME` (recorded `nas sync` runs). A point is `{ id, time, epoch, label, tier, size }`; **tier** is by age (hourly up to a day, daily to a week, weekly to 5 weeks, monthly to a year, yearly after). A target that fails is a row with an `error` (unreachable, not initialized, NAS not mounted), never a failure of the whole timeline; `--local` leaves out the targets that need the network so the screen opens at once. `BXRIG_TIMELINE_FILE` injects a timeline (tests); `BXRIG_NOW_EPOCH` fixes the clock.
- **The screen:** places as rows over a time axis (newest on the right; zoom 1 day, 1 week, 1 month, 3 months, 1 year, all; the axis grows to keep the chosen backup in view), points coloured by tier, a guide line through the chosen moment, the chosen backup as a card with the older ones stacked behind it, counts by tier for the place, and the brand gradient with Powered by BoxLang. Keys: left and right (or h l) through time, up and down (k j) between places, plus and minus zoom, enter open, d diff, r restore, e export, s send, n back up now, / filter in the browser, ? help, q or esc leave; the mouse picks a point, a place or a zoom chip and the wheel moves through time. Under 90 by 30 cells it asks for a bigger window.
- **What it runs:** it only runs `bxrig` commands, and **every change goes through a plan first**: it runs the command with `--dry-run`, shows the plan, and runs it with `--yes` only on `y`. Open: `backup data files ID --json`, `backup config show ID --json` or `backup snapshots changes N`. Restore: `backup data restore ID --to=~/Restored/ID [--include=PATH]`, `backup config restore ID [--only=PATH]` or `backup snapshots restore N PATH` (a folder must be picked first). Export: `backup export data|config`. Send: `backup send ID --from=PLACE --to=PLACE` (file backups only; a destination picker). Back up now: `backup data run`, `backup config now` or `backup snapshots create`. Config snapshots reach a NAS or the cloud through the data backups (they are in its include list).
- **`--demo`** shows a made-up timeline (every kind of place and every tier) and runs nothing: plans and results say what the command would have been. `tools/record-timemachine.py` records the demo in a pseudo-terminal (pyte, Pillow, ffmpeg) into named screenshots and a video.
- **Verified:** `tests/time_machine_test.bxs` (the model, the keys and intents, the date maths, and what each screen shows via `render_to_string`) and `tests/timeline-test.sh`. **Not yet tried:** against real restic repositories, a real NAS or snapper on Btrfs; with a real terminal beyond the recorded demo.

- **`backup status [--json]` (read only, for the System bar panel):** `{ now, health, warn_count, rows }` with one row per kind in the order config, system, data: `{ id, label, kind, tool, configured, count, last, last_epoch, last_ago, next, next_epoch, size, size_text, health, note, action, action_text }` (data adds `targets` and `schedule`). Derived from the existing layers: `BackupTimeline.configRow` and `systemRow`, `BackupConfig.readSettings` (auto), `BackupSnapshots` (tool, configs, the snapper timeline timer), `BackupData.readAll` (targets, schedule and `data.runs`, the last success and last failure `backup data run` records per target in backup.json) and `Systemd.nextRun` (`show --property=NextElapseUSecRealtime --timestamp=unix --value`). Health: `ok` within the limit and no failure; `warn` older than the limit (config 30 days; system 2 days with the timeline timer on, else 14; data 6 hours hourly, 2 days daily, 14 days off), the last run failed, the scheduled unit failed or restic is missing; `none` nothing to judge. `size` is bytes (config snapshots only, else 0). `action` is the argv words that back it up now, `[]` when not possible: the commands that already exist (`backup config now`, `backup snapshots create --yes`, `backup data run --all --yes`), so there is no `backup now`. Exit 0. The time maths moved to `util/Clock.bx` (`BackupTimeline` forwards to it, so `BackupData` can stamp a run without a class cycle). Tests: `tests/backup-status-test.sh`, `backup_status_test.bxs`.

### 13.48 The mail catcher (decided with the owner 2026-11-14)

- **Command:** `mail start [--keep] [--smtp-port=N] [--ui-port=N] [--yes] [--dry-run]|stop|status|remove [--keep-data] [--yes]|list [--limit=N]|show ID|delete ID [--yes]|clear [--yes]|open [ID]|test [--to=ADDR] [--subject=TEXT]|env [--json]`. A development inbox: Mailpit (`axllent/mailpit`) in a container named `bxrig-mail`, SMTP on `127.0.0.1:1025`, web inbox and REST API on `127.0.0.1:8025` (both ports can be changed; ports are 1024 to 65535 and must differ, else exit 4). Everything is bound to `127.0.0.1`. The engine is the one `db engine` chose (podman by default).
- **Thrown away on stop.** Without `--keep` the container runs with `--rm` and no volume, so `stop` deletes it and its mail. With `--keep` it runs with `--restart unless-stopped`, the folder `~/.local/share/bxrig/mail` bind-mounted at `/data:Z` and `MP_DATABASE=/data/mailpit.db`, so mail survives stop and start. `remove` deletes the container and the stored mail; `--keep-data` keeps the folder. `start`, `remove`, `clear` and `delete` plan first (exit 2 without `--yes`, `--dry-run` exits 0); `test`, `open`, `list`, `show`, `env`, `stop` and `status` act at once. The ports and `keep` are remembered in `mail/meta.json`.
- **Container settings:** `MP_SMTP_AUTH_ACCEPT_ANY=1`, `MP_SMTP_AUTH_ALLOW_INSECURE=1` (an app that logs in works with any user and password, no TLS) and `MP_MAX_MESSAGES=5000`, taken from Mailpit's own Docker example.
- **API used** (from Mailpit's swagger): `GET /api/v1/messages?limit=N` (`total`, `unread`, `messages[]` with `ID`, `From{Name,Address}`, `To[]`, `Subject`, `Created`, `Size`, `Attachments` as a count, `Read`, `Snippet`), `GET /api/v1/message/{ID}` (`Text`, `HTML`, `Cc`, `Bcc`, `Date`, `Attachments[]` with `FileName`, `ContentType`, `Size`), `DELETE /api/v1/messages` (all, or a body `{ "IDs": [...] }`), `POST /api/v1/send` (`From{Email,Name}`, `To[{Email}]`, `Subject`, `Text`) and `GET /view/{ID}.html` (opened with `xdg-open`). HTTP goes through `curl`. Without an answer, anything that needs the API exits 4.
- **JSON names differ from the API's on purpose** (`mid`, `sender`, `sender_address`, `recipient`, `subject_line`, `received`, `bytes`, `attachment_count`, `seen`, `preview`; for `show`: `to_list`, `cc_list`, `bcc_list`, `sent`, `body_text`, `body_html`, `files[]` with `file_name`, `type`, `bytes`; for `test`: `recipient`, `subject_line`): MatchBox keeps the capitalisation of the first spelling of a key it sees, so a field called `id` came out as `ID` after parsing the API's `ID`. Fields that do not clash (`total`, `unread`, `smtp`, `web`) keep their names.
- **`mail env`** prints the SMTP settings (host, port, no encryption, no login needed) for a generic list, BoxLang and ColdBox (words only: the exact setting names were not checked), Laravel (`.env`), Spring Boot, Node (nodemailer) and plain environment variables.
- **Control Center page `Mail`:** table of from, received, size, attachment mark and subject; the detail box shows the headers and the wrapped text body of the highlighted message. `d` plans `mail delete ID`, `c` plans `mail clear`, `o` runs `mail open ID` at once, `t` runs `mail test`, `r` reloads. ## 14. Install and the setup wizard (decided with the owner 2026-11-10; install, wizard and the init engine are built, the pages' later commands are not)

### 14.1 Install

`bootstrap/install.sh [--yes] [--dry-run]` is the one install command. It prints the plan, asks one `Proceed? [Y/n]` at a terminal (without a terminal it needs `--yes`, else exit 2; `--dry-run` exits 0), then runs, in order: packages with yay and Rust, toolchains (mvm, bvm, BoxLang, nvm and Node, MatchBox), the bxrig binary, and the core apps (`bxrig profile-install core --yes`). External installer scripts run without a gate (section 2, rule 8). **MatchBox (decided 2026-11-18, replaces the S3 build of the branch head):** the toolchains stage installs MatchBox through mvm. Stable by default: `mvm install latest`, `mvm use latest`, only when no MatchBox is installed (a re-run leaves an installed one alone). `--snapshot` or `BXRIG_MATCHBOX_CHANNEL=snapshot`: `mvm install snapshot`, `mvm use snapshot` on every run (mvm skips an unchanged build). `--matchbox-branch REF [--matchbox-repo OWNER/NAME]` (`BXRIG_MATCHBOX_BRANCH`, `BXRIG_MATCHBOX_REPO`; the default repo is `toolchain.matchbox.repo`, the default branch of the alias `--matchbox-from-source` is `toolchain.matchbox.ref`, `bxrig`): `git clone --depth 1 --branch REF`, `cargo build --release --features bif-tui`, installed as `$BXRIG_HOME/matchbox/bin/matchbox` with `build.info` (repo, branch, commit, source); it is first on the installer's PATH (never replaces mvm's MatchBox) and is rebuilt only when the repo, the branch or the remote head (`git ls-remote`, unreadable counts as moved) changed. Choosing `--snapshot` removes an earlier branch build; no option leaves it. REF `^[A-Za-z0-9._/@+-]+$` (no leading dash, no `..`, no leading or trailing slash) and OWNER/NAME are validated, invalid is exit 2, `--snapshot` with a branch is exit 2, and values reach git only as argv items. `BXRIG_MATCHBOX_FILE=PATH` installs a local build instead (source `file`). **Capability, not version:** no check compares the MatchBox version with `box.json`. Only the stage that compiles bxrig needs a capable MatchBox: the binary stage without `--binary` (so also the stage of a github source and `scripts/setup-local.sh`) runs `matchbox probe.bxs`, a three line script that creates `createObject( "rust", "tui.TUI" )`, draws a frame and prints a marker; a MatchBox built without `bif-tui` (stable and snapshot today) stops it with exit 1 and `This MatchBox (VERSION) cannot compile BxRig ... use --matchbox-branch bxrig`, never switching MatchBox on its own. With `--binary PATH` (the web installer's prebuilt bxrig) any MatchBox is fine; the toolchains stage only notes whether the MatchBox can compile bxrig, and `install.sh check` prints `matchbox: VERSION (compiles BxRig: yes|no)`. `--snapshot`, `--matchbox-branch`, `--matchbox-repo` and `--matchbox-from-source` are accepted by the full install and by `toolchains --yes`; `--dry-run` prints the MatchBox line and step. `install.sh check` is the read-only report; `packages|toolchains|binary|core --yes` re-run one stage. **Disk (decided 2026-11-18, from a real Arch container run):** a single stage needs 5 GB free in `$HOME` (`MIN_FREE_GB`); the whole install needs 8 GB (`FULL_FREE_GB`), checked up front, so a machine with 5 to 7 GB cannot pass stage 1 and fail at stage 2 after Rust was installed. The 8 GB: Rust about 2.5 GB (6 GB free before, 4 GB after), packages about 1.3 GB (pacman: 1334 MiB), the MatchBox branch build with its cargo target directory about 3 GB, Java, mvm, bvm, BoxLang and the bxrig binary about 0.5 GB, 0.7 GB of headroom. The plan prints `Disk: need 8 GB for the whole install, N GB free (ok|not enough)`; the real run exits 1 with `Not enough free disk space ... Nothing was changed.` before any stage; `--dry-run` only reports; `check` prints `disk-free: N GB (need 8 for the whole install)`. **Closing line:** the core profile has no apps, so the last stage says `Nothing to install. Choose the desktop and apps with \`bxrig init\`.` and the install ends with `Tools installed. Run \`bxrig init\` for the desktop and apps.` (at a terminal: `Tools installed.` and the wizard starts). **mvm failures:** `mvm install` is tried three times and its own output is shown; only output with 403, 429 or `rate limit` gets the rate-limit hint, anything else (a proxy, a TLS-inspecting firewall that mvm does not trust) gets `Could not reach GitHub. Behind a corporate proxy or a TLS-inspecting firewall? ...` and the branch-build alternative `install.sh toolchains --yes --matchbox-branch bxrig`. When the wizard exists the install ends by starting it at a terminal.

**Required vs optional toolchains (decided 2026-11-10):** the install always adds BoxLang (Java 21, bvm, mvm, MatchBox, Rust). nvm and Node.js are no longer part of it; they are the optional JavaScript toolchain: `bxrig toolchain node [--yes] [--dry-run] [--json]` runs the pinned nvm installer from `box.json` `toolchain.nvm` (an external script: its URL is in the plan, it adds nvm to your shell startup files) and `nvm install lts/*`, skipping what is already there. Bun and Deno are catalog apps (`install bun deno`).

### 13.53 Shared helper classes (decided with the owner 2026-11-14, code review refactor)

One home per concept; command classes hold small collaborators in `variables.*` (there are no base classes on MatchBox).

- **Output: `Cli.say( command, code, data, asJson, lines = [], dry = false )`, `Cli.fail( command, code, msg, asJson )`, `Out`.** `Out` is the same bound to one command name (`variables.out = new bxrig.Out( variables.cli, "time" )`): `say`, `fail`, `usage` (2), `precondition` (4), `failed` (6), `sub( command )`. Every method returns the exit code. A class must not create `Out` from inside `Out`/`Cli.scoped` chains of its own class (MatchBox overflows the stack when a class `new`s itself).
- **Processes: `Proc`.** `exec( argv, timeout )` never throws (`{ exitCode, output, timeout }`, 127 and the reason when the program cannot start), `raw` may throw, `has( name )` is `command -v` with the name as an argument (never run the tool), `works( name )` is `name --version`, `isRoot()`, `self( args, timeout )` runs BxRig itself (`BXRIG_SELF`). `Installer.proc()` hands the same injected test runner to a class; `Installer.hasCommand` is `Proc.has`, so a tool without `--version` counts as installed.
- **Paths: `Env`.** `BXRIG_*_HOME`, then `XDG_*_HOME`, then `$HOME` for every folder: `xdgConfig( sub )`, `xdgData`, `xdgState`, `xdgCache` (shared with other programs) and BxRig's own `config`, `data` (`BXRIG_DATA_HOME` is the folder itself), `state`, `cache`. A user with `XDG_CONFIG_HOME` set now gets every BxRig file under it (`bxrig/`, `menus/`, `nvim/`, `strata/`); `tests/paths-test.sh` guards it. `new bxrig.Env( { HOME: "/h" } )` replaces the real environment in unit tests.
- **Text: `Text`** (`merge`, `pad`, `padLeft`, `lines`, `nl`).
- **Desktop entries: `DesktopEntry`.** `parse` (exact-case keys, only the `[Desktop Entry]` group, `launcher` for BxRig's own `X-BxRig-Launcher` entries), `dirs( withFlatpak )` (`BXRIG_APPS_DIRS`, older `BXRIG_DESKTOP_DIRS`), `entries( dirs, launchers, needExec )`, `iconName`, `cleanExec`, `render( lines )`. The Apps page leaves BxRig's launchers out; the `apps` launcher grid keeps them.
- **Package layout.** `src/bxrig/` has one class per command or feature (152 classes, 4,982 lines of generated `*Data.bx` among them); `src/bxrig/util/` has the 23 shared helpers, reached as `bxrig.util.NAME`: `Cli`, `Out`, `Exit`, `Mutation` (plans and dry runs), `Proc`, `Env`, `Text`, `Fmt`, `Names`, `JsonStore`, `SystemFile`, `SystemdUnit`, `Systemd`, `Pacman`, `Aur`, `Http`, `Urls`, `Desktop`, `DesktopEntry`, `Ini`, `Props`, `Lua` and the generated `Version`. A helper never holds a command's job and a command never holds a helper's; `tests/dry-test.sh` keeps the copies from coming back.
- **Command registry.** `docs/reference/cli.json` holds every command (name, group, summary, usage, examples, flags with types, note). `bootstrap/gen-docs.sh` writes `commands.md`, `command-flags.md`, `HelpData.bx` (`bxrig help`) and `CommandFlagData.bx` from it and fails when `Main.bx` has a command the file lacks (or the reverse), an example names no command, or a usage line uses a flag the command does not list. `CommandSpec` answers flags and usage at run time.
- **Unknown command exit.** A command that is not in `Main.bx` prints "Unsupported command" and exits 2 (it exited 0 before); the flag whitelist has no duplicates.
- **Tests.** `tests/lib/harness.sh` (binary, tmp, `fail`, `stub`, `code`), `tests/run-all.sh` (discovery, parallel), `tests/dry-test.sh` (ratchet of copied helpers and of tests missing from CI).

### 13.58 `vpn`: one list of VPNs with data-driven adapters (decided with the owner 2026-11-17)

The top bar has a VPN icon (plugin `bxrig/vpn`, section 13.59); this is the command behind it. One pick-one list with two groups: **Network profiles** (saved NetworkManager connections of type `vpn` or `wireguard`, through `nmcli`) and **VPN apps** (NordVPN, NordLayer, Tailscale, Mullvad).

- `vpn list [--json]` the installed providers and profiles with their state; **an empty list, exit 0, when nothing is installed** (the bar icon hides itself then). `data`: `{ providers: [ { id, name, group (profiles|apps), kind, state, connected, location, detail, can_pick, coexist, verified, note } ], connected: [ids], allow_several, install: [ { id, name, install } ] }`. `state` is `connected`, `connecting`, `disconnected`, `login` (log in first), `unavailable` (daemon not running) or `unknown`. A profile's id is `nm:NAME`.
- `vpn status [NAME]` what is connected (one provider with NAME). `vpn locations NAME` the places it can connect to: `{ provider, can_pick, current, locations: [ { value, label } ] }` with the reserved first entries `default` (connect as it is) and, where the provider can clear a choice, `none` (Tailscale: no exit node), then the provider's own list (NordVPN countries, Tailscale exit nodes, Mullvad countries and cities, NordLayer gateways).
- `vpn connect NAME [--location=VALUE]` and `vpn disconnect [NAME]` start or stop a program, so they act at once and take `--dry-run` (the exception of 2.11). Without a NAME `disconnect` stops everything that is connected. **Default: one at a time**: connecting first disconnects what is connected. `vpn set allow_several=true|false --yes` (saved in `~/.config/bxrig/vpn.json` through the config service, `--dry-run` shows the plan) lifts that, for Tailscale next to another VPN; a note says that two VPNs can clash on routes and DNS. Not tested against a real NordVPN plus Tailscale: the owner is to try it.
- Exit codes: 0 done or nothing to do; 2 bad usage, an unknown name, a bad `--location` (no leading dash, plain characters, up to 80), `set` without `--yes`; 4 no VPN installed (status, connect, disconnect, locations), a known provider that is not installed, or no NetworkManager for an `nm:` name; 6 a command failed.
- **Adapters are data.** `catalog/vpn-providers.json` (a resource) has one object per app: `binary`, `install` (catalog id), `status { argv, parser }`, `connect`, `connect_to` (with `{location}`) or `select` plus `select_order` (`before` or `after`, for apps that pick a place in a separate command) and `select_none`, `disconnect`, `locations { argv, parser }`, `default_label`, `none_label`, `coexist`, `verified`, `note`. The code (`VpnAdapters`) has no branch for any provider; the only code is the named parsers in `VpnParsers` (`nordvpn`, `nordlayer`, `tailscale`, `mullvad`, `words`). A provider of your own goes in `~/.config/bxrig/vpn-providers.json` (`{"providers":[...]}`, adds or replaces by id). Argv templates are arrays (rule 9): `{location}` is one argument, `{location*}` the location split on spaces.
- **Verified against the vendors' documentation on 2026-11-17** (each adapter's `note` says exactly what): NordVPN `status`, `connect`, `disconnect`, `countries` (support.nordvpn.com); Tailscale `up`, `down`, `set --exit-node=` (an empty value clears it), `exit-node list`, `status --json` (tailscale.com/kb/1080/cli); Mullvad `status`, `connect`, `disconnect`, `relay list`, `relay set location COUNTRY [CITY]` (mullvad.net); `nmcli connection show|up|down`, `-t` escaping of `:` (NetworkManager manual). **Not verified:** NordVPN `connect COUNTRY` by name (from `nordvpn help connect`, the page shows `connect CODE SERVER`); the exact text of `mullvad status` and `relay list` between app versions; the Tailscale JSON field names (the page only says "detailed JSON"); NordLayer `status`, `gateways` and `disconnect` (help.nordlayer.com confirms only `nordlayer connect GATEWAY-ID` and `nordlayer settings set`), so its parsers are tolerant and its adapter says `partial`.
- **Catalog:** `nordlayer` is a new catalog app (`aur`, target `nordlayer`, kind desktop, optional; the AUR RPC listed it on 2026-11-17 as version 3.6.0, a community package of the vendor's `.deb` from downloads.nordlayer.com; the vendor ships only `.deb` and `.rpm`, so there is no vendor package for Arch). The wizard's VPN question offers it (no extra step: log out and in, then log in with the app). Check the package before relying on it: it is not maintained by NordLayer.
- **Left out on purpose:** ExpressVPN and Surfshark (owner); Proton VPN (its command line was not verified: no adapter row until it is); WireGuard `wg-quick` (needs root for every up and down: a NetworkManager WireGuard profile covers it).
- The NordVPN post-install steps stay as they were: `vpn nordvpn setup [--yes]` (13.20) is routed through the same class.
- Tests: `tests/vpn_test.bxs` (parsers, adapters, the commands with a fake runner), `tests/vpn-test.sh` (fake `nordvpn`, `tailscale`, `nmcli`; no real VPN is touched).

### 13.66 The screensaver (decided with the owner 2026-11-18)

- **What it is.** After a while idle, terminal art in the theme's colours on every monitor, then the lock. Six effects take turns, a minute each, from a random first one: `sweep` (BXRIG in DOS Rebel with a gradient sweeping across it), `laptop` (the About laptop with a glint crossing BX), `rain` (BoxLang code falling in columns), `clock` (the time in DOS Rebel, drifting), `stars` (a starfield) and `logo` (your text in DOS Rebel or a picture in half blocks, drifting). Every effect moves, so nothing stays on the same pixels. Any key, click, scroll or mouse move closes it (mouse moves need MatchBox's `tui.set_mouse_motion`; events in the first half second are ignored).
- **Commands.** `screensaver [status] [--json]`; `on|off [--yes]` (off keeps the lock); `set screensaver=SECONDS lock=SECONDS effects=NAME,NAME [--yes]` (whole seconds, 0 for never, the lock after the screensaver); `logo text TEXT|image PATH|reset [--yes]` (1 to 10 letters, digits, spaces or `. _ ! : -`; a png, jpg, gif, webp or svg); `effects [--json]`; `start [--effect=NAME]`; `stop`; `preview [EFFECT]` (in this terminal); `run [--effect=NAME]` (what each window runs). A change without `--yes` is a plan. Exit 0, 2 usage, 4 no Hyprland, no terminal that can name its window, or not a terminal.
- **Settings:** `~/.config/bxrig/screensaver.json` `{ enabled, screensaver, lock, effects, logo }`; defaults on, 150 s, 300 s, every effect, the text BXRIG. A value that is not valid keeps its default.
- **Idle (Noctalia, docs.noctalia.dev services/idle).** Two behaviors in `[idle]`, `behavior_order = ["bxrig_screensaver", "bxrig_lock"]`: `bxrig_screensaver` is `action = "command"`, `command = "'BXRIG' screensaver start"`, `resume_command = "'BXRIG' screensaver stop"`, so coming back closes it; `bxrig_lock` is Noctalia's own `action = "lock"`. Both count from the start of idle and respect idle inhibitors (a video, `toggle stay-awake`). The starter `config.toml` carries the section; a change is sent to a running Noctalia with `noctalia msg config-set` (reported as `applied`, `not running` or `skipped`). `hypridle` is no longer started or installed: BxRig never wrote a config for it.
- **Windows (Hyprland).** `start` opens one terminal per monitor from `hyprctl monitors -j`, with the class `bxrig-screensaver` (ghostty, kitty, alacritty or foot, the xdg-terminals.list one first), through `hyprctl dispatch exec "[monitor NAME] ..."` and, when that fails, the Lua form `hl.dsp.exec_cmd(CMD, { monitor = NAME })`. The Hyprland module's window rule makes the class full screen with no animation, border, corners, shadow or blur. `start` does nothing when one is already open; `stop` kills the pids `hyprctl clients -j` gives for the class. With neither Hyprland nor Plasma, `start` exits 4.
- **Plasma (2026-11-18).** `ScreensaverPlasma`: the idle watcher is a user service, `~/.config/systemd/user/bxrig-screensaver-idle.service`, running `swayidle -w timeout SECONDS "BXRIG screensaver start --idle" resume "BXRIG screensaver stop"` (KWin implements ext-idle-notify-v1); `on`, `off` and `set` write, enable and restart it, or disable it, and name `swayidle` when it is missing (`setup plasma` installs it). `start --idle` first asks `org.freedesktop.PowerManagement.Inhibit.HasInhibit` and does nothing while something holds the screen awake, since KWin's idle timer has been reported to ignore inhibitors. `start` writes `templates/kwin-screensaver.js` to `~/.local/share/bxrig/kwin/`, loads it once over D-Bus (`org.kde.kwin.Scripting.loadScript`, then `start`), and opens one terminal per enabled output from `kscreen-doctor -j`; the script sends each new `bxrig-screensaver` window to a screen without one, full screen, above everything, without a border, off the taskbar and switcher (a forced screen window rule is not applied when a window opens on Wayland, KDE bug 514357). `stop` kills the terminals `pgrep -f` finds by the class. The lock is Plasma's own: `kscreenlockerrc [Daemon] Autolock` and `Timeout` in whole minutes (rounded up), `lock=0` sets `Autolock=false`; a running lock daemon is told with `qdbus6 org.freedesktop.ScreenSaver /ScreenSaver configure` (best effort). Not yet run on a real Plasma session: written against the KWin scripting API docs and checked with stubs.
- **UI.** Menu *System > Screensaver* (start, preview, settings, on, off, three timings, logo reset); the Look page's *Screen* group (a switch and a timing choice: 2.5/5, 5/10, 10/20, 15/30 minutes); the wizard's Look page asks when it starts (2.5, 5 or 10 minutes, the lock at twice that, or off).

## Distributions (decided with the owner 2026-11-20)

- **Targets:** CachyOS and Arch (pacman, AUR), openSUSE Tumbleweed and Slowroll (zypper), Ubuntu 26.04 LTS and Debian 13 (apt). `util.Distro` reads `/etc/os-release` (`ID`, `ID_LIKE`, `VERSION_ID`); `BXRIG_DISTRO` (arch, suse, debian, ubuntu) overrides it, and tests and CI set it to `arch`. An unknown system reads the Arch catalog, and `setup` and the installer refuse it.
- **Catalog split:** `catalog/apps.json` (schema 4) says what an app is; `catalog/install/DISTRO.json` (schema 1) says how to install it: `defaults` (`terminal`), `names` (Arch package name to this distribution's, `""` for none needed), `repos` (extra repositories, each with `for` packages, a `check` path under `/etc`, `commands` and `files`), and `apps` (`source` + `targets`, and on Arch `repo`/`pkgbuild`/`aur_targets`/`script`). `extends` merges `names`, `apps` and `defaults` from a parent; a child's `repos` replaces the parent's. `ubuntu.json` extends `debian.json`. `Catalog.load(distro)` merges the entry into each app; an app without one is in `unavailable` and is not offered. Web apps need no entry.
- **Sources:** arch `pacman aur pkgbuild script unresolved`; suse `zypper flatpak script`; debian and ubuntu `apt flatpak script`. `catalog check` checks every install file (`checkAll`); `catalog coverage` reports offered and unavailable per distribution; `catalog list|show --distro=D` reads another one.
- **Package layer:** `util.Packages().native(proc, distro)` gives `Pacman`, `Zypper` or `Apt` with one interface (install, remove, upgrade argv, installed, versions, search rows, pending updates). Arch names are translated through `names` everywhere setup and the installer name a package. Apt runs `apt-get update` before an install or upgrade.
- **Flatpak fallback:** an app the distribution does not package is installed from Flathub with `flatpak install --user`; the plan adds `flatpak` itself and the Flathub remote when missing. Never as root.
- **Repositories:** Debian 13 adds `trixie-backports` (Hyprland, its tools, quickshell; skipped when an apt source already names it, `check_text`, and its packages install with `-t trixie-backports`, `release`, so their newer libraries come from it too); Debian 13 and Ubuntu 26.04 add Noctalia's apt repository (`pkg.noctalia.dev`, keyring package then the suite's `.sources` file). Added only when a package in the plan needs them and their file is not there yet.
- **Defaults:** Debian's terminal is kitty (no ghostty package); the rest use ghostty.
- **Arch-only:** the AUR (`pkg search --aur`, `pkg install --aur`), `kernel`, the boot splash (mkinitcpio), xremap's install (configuration works once it is installed), Nerd Fonts packages (`appearance font install` exits 4 elsewhere).
- **`catalog map DISTRO [--write] [--json]`:** run on that distribution; for each app tries the Arch names through `names`, then without `-bin`/`-git`/`-desktop-bin`/`-electron`, then Flathub by exact name; reports kept, found, flatpak, missing, and the Arch names BxRig installs itself that the distribution lacks. `--write` updates the install file. Exit 4 off that distribution.
- **Bootstrap:** `install.sh` and `web-install.sh` pick pacman, zypper or apt-get from `os-release`; yay only on Arch.
- **Not done yet:** the boot splash through dracut or initramfs-tools, xremap packages off Arch, Nerd Fonts off Arch, Packman codecs on openSUSE.
- **Tests:** `tests/distros_test.bxs` (families, the backends' argv and parsers, names, the merged catalogs, repo steps) and the CI containers (Tumbleweed, debian:trixie, ubuntu:26.04: install, `catalog check`, `setup hyprland --dry-run`).

## Scheduler (decided with the owner 2026-11-22)

- One scheduler for everything BxRig runs on a timer: a BoxLang scheduler class run by `boxlang schedule` in the user service bxrig-scheduler.service. Groups, pause and resume per group, a history and stats per task.

- The JVM only dispatches: every run is `bxrig scheduler exec NAME`, which runs the command, records it (history/NAME.jsonl, last 500) and notifies. The runner writes each task's getStats() (with next_local and last_local on this machine's clock) for the next run time.

It adds update-check, backup-data (when backups are scheduled) and boxlang-check, and turns off bxrig-update-check.timer and bxrig-backup.timer; from then on `update notifications` and `backup data schedule` change those tasks. Without BoxLang the timers stay as they were.
- Exit 10 from a task is "needs attention" where the task lists 10 in ok_codes (update-check, boxlang-check); notify modes are failure (default), attention, always and never.

### 13.67 BoxLang agents: `ai agents` (decided with the owner 2026-11-24)

bx-agents has a full command line (`bxAgents`, every verb on one project: the current folder or `--projectRoot`), so BxRig does not repeat it (`AiAgentHub.bx`).
